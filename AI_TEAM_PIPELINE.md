## 1. Состав команды

## 3. Золотое правило: ОБЯЗАТЕЛЬНЫЕ ВОПРОСЫ

**Каждая роль ОБЯЗАНА задать вопросы перед началом работы. Без ответов работа НЕ начинается.**

### 3.1 Почему это критично

- Предотвращает реализацию не того, что нужно
- Выявляет скрытые требования на ранних этапах
- Обеспечивает взаимопонимание между ролями
- Снижает количество переделок

### 3.2 Протокол согласования

```
┌──────────┐    Вопросы     ┌──────────┐    Ответы     ┌──────────┐
│   Роль   │ ────────────── │ Команда  │ ───────────── │   Роль   │
│(инициатор)│                │(адресат) │               │(инициатор)│
└──────────┘                └──────────┘               └──────────┘
                                                          │
                                                    Подтверждение
                                                    "Могу начать"
                                                          │
                                                          ▼
                                                    НАЧАЛО РАБОТЫ
```

### 3.3 Формат запроса на согласование

Каждая роль перед началом работы отправляет запрос:

```markdown
## Запрос на согласование: [Роль] → [Этап]

**Задача:** [Описание]
**ЧТЗ:** [Ссылка]

### Мои вопросы:
1. [Вопрос 1]
2. [Вопрос 2]
3. [Вопрос 3]

### Мой план:
- [ ] Шаг 1
- [ ] Шаг 2
- [ ] Шаг 3

**Статус:** Жду подтверждения.
```

**РАБОТА НАЧИНАЕТСЯ ТОЛЬКО ПОСЛЕ ПОЛУЧЕНИЯ ПОДТВЕРЖДЕНИЯ.**

## 4. Детальные этапы конвейера

### ЭТАП 1: Аналитик

#### Универсальный перечень задач Аналитика

| ID | Задача | Обязательная | Выход |
|----|--------|-------------|-------|
| A-001 | Задать уточняющие вопросы заказчику | ДА | Список вопросов + ответы |
| A-002 | Изучить существующий код и архитектуру | ДА | Контекст проекта |
| A-003 | Выявить нефункциональные требования | ДА | NFR список |
| A-004 | Описать User Stories с Acceptance Criteria | ДА | User Stories |
| A-005 | Спроектировать изменения в БД (если нужны) | Если применимо | SQL миграции |
| A-006 | Спроектировать API спецификацию | Если применимо | API spec |
| A-007 | Описать UI/UX требования | Если применимо | UI требования |
| A-008 | Создать декомпозицию задач (TASK-XXX) | ДА | Список задач |
| A-009 | Определить зависимости между задачами | ДА | Dependency graph |
| A-010 | Согласовать ЧТЗ с заказчиком | ДА | Утверждённый ЧТЗ |
| A-011 | Передать ЧТЗ в разработку | ДА | ЧТЗ + декомпозиция |

#### Контрольная точка Этапа 1

```
ВЫХОД ЭТАПА 1 (передаётся Разработчику):
├── ЧТЗ документ (утверждённый)
├── Декомпозиция задач (TASK-BCK, TASK-FRT, TASK-TST)
├── API спецификация
├── Схема БД (миграции)
└── Критерии приёмки
```

### ЭТАП 2: Разработчик

#### Универсальный перечень задач Разработчика

| ID | Задача | Обязательная | Выход |
|----|--------|-------------|-------|
| D-001 | Задать вопросы по ЧТЗ Аналитику | ДА | Понимание требований |
| D-002 | Изучить существующий код и паттерны | ДА | Контекст реализации |
| D-003 | Реализовать backend (API, сервисы, БД) | Если есть TASK-BCK | Код |
| D-004 | Реализовать frontend (компоненты, страницы) | Если есть TASK-FRT | Код |
| D-005 | Написать Unit-тесты | ДА | Тесты |
| D-006 | Запустить все тесты (`npm test`) | ДА | Результаты тестов |
| D-007 | Проверить lint (`npm run lint`) | ДА | Чистый lint |
| D-008 | Проверить типы (`npx tsc --noEmit`) | ДА | Без ошибок типов |
| D-009 | Протестировать вручную в браузере | ДА | Ручная проверка |
| D-010 | Обновить документацию | Если требуется | Обновлённые docs |
| D-011 | Передать на тестирование | ДА | Готовый код |

#### Порядок реализации задач

```
1. Прочитать ЧТЗ полностью
2. Задать вопросы Аналитику (ОБЯЗАТЕЛЬНО)
3. Изучить существующие паттерны в проекте
4. Реализовать задачи в порядке из ЧТЗ:
   a. TASK-BCK-xxx (Backend)
   b. TASK-FRT-xxx (Frontend)
   c. TASK-INF-xxx (Infrastructure, если есть)
5. Написать Unit-тесты для всей новой логики
6. Запустить: npm test && npm run lint && npx tsc --noEmit
7. Проверить вручную
8. Передать Тестировщику
```

#### Контрольная точка Этапа 2

```
ВЫХОД ЭТАПА 2 (передаётся Тестировщику):
├── Реализованный код (все TASK-XXX выполнены)
├── Unit-тесты (покрытие >= 60%)
├── Результат npm test: все PASS
├── Результат npm run lint: без ошибок
├── Результат npx tsc --noEmit: без ошибок
└── Список реализованных TASK-XXX
```

## 5. Разбиение больших задач на этапы

### 5.1 Критерий "большой задачи"

Задача считается **большой**, если:
- Декомпозиция содержит **более 10 задач** (TASK-XXX)
- Оценка времени **более 16 часов**
- Затронуто **более 3 модулей** системы
- Требуется **изменение архитектуры**

### 5.2 Принцип разбиения

Большая задача разбивается на **подэтапы**, каждый из которых проходит полный цикл конвейера:

```
БОЛЬШАЯ ЗАДАЧА
├── Подэтап 1 (Фундамент)
│   ├── Аналитик → ЧТЗ-1
│   ├── Разработчик → Код-1
│   └── Тестировщик → Проверка-1
│
├── Подэтап 2 (Основной функционал)
│   ├── Аналитик → ЧТЗ-2
│   ├── Разработчик → Код-2
│   └── Тестировщик → Проверка-2
│
├── Подэтап 3 (Дополнительный функционал)
│   ├── Аналитик → ЧТЗ-3
│   ├── Разработчик → Код-3
│   └── Тестировщик → Проверка-3
│
└── Подэтап N (Финализация)
    ├── Аналитик → ЧТЗ-N
    ├── Разработчик → Код-N
    └── Тестировщик → Финальная приёмка
```

### 5.3 Шаблон разбиения большой задачи

```markdown
# План реализации большой задачи: [Название]

## Общее описание
[Описание бизнес-задачи]

## Разбиение на подэтапы

### Подэтап 1: [Название] (Приоритет: Critical)
**Цель:** [Что достигается]
**Задачи:** TASK-XXX-001 ... TASK-XXX-005
**Оценка:** X часов

### Подэтап 2: [Название] (Приоритет: High)
**Цель:** [Что достигается]
**Зависит от:** Подэтап 1
**Задачи:** TASK-XXX-006 ... TASK-XXX-010
**Оценка:** X часов

### Подэтап N: [Название] (Приоритет: Medium)
**Цель:** [Что достигается]
**Зависит от:** Подэтап N-1
**Задачи:** TASK-XXX-0xx ... TASK-XXX-0yy
**Оценка:** X часов
```

### 5.4 Правила подэтапов

1. **Каждый подэтап — автономен**: Его можно протестировать и задеплоить независимо
2. **Внутри подэтапа — полный цикл**: Аналитик → Разработчик → Тестировщик
3. **Между подэтапами — вопросы обязательны**: Тестировщик подтверждает готовность перед началом следующего
4. **Регрессия после каждого подэтапа**: Тестировщик проверяет, что предыдущий функционал не сломан

## 6. Петля обратной связи (Feedback Loop)

### 6.1 Когда Тестировщик нашёл баг

```
Тестировщик находит баг
        │
        ▼
Регистрирует BUG-XXX с severity/priority
        │
        ▼
Передаёт Разработчику
        │
        ▼
Разработчик задаёт вопросы (если нужно уточнить)
        │
        ▼
Разработчик фиксит баг
        │
        ▼
Передаёт обратно Тестировщику
        │
        ▼
Тестировщик проверяет:
  1. Баг исправлен? (Verification)
  2. Ничего не сломано? (Regression)
        │
    ┌───┴───┐
    │       │
  PASS    FAIL
    │       │
    ▼       ▼
 Закрыть  Переоткрыть
  баг     баг → Разработчику
```

### 6.2 Когда Расхождение с ЧТЗ

```
Тестировщик видит расхождение кода и ЧТЗ
        │
        ▼
Фиксирует расхождение
        │
        ▼
Вопрос к Аналитику:
"В ЧТЗ: X. В коде: Y. Как правильно?"
        │
    ┌───┴───┐
    │       │
  ЧТЗ     Код
  верно   верен
    │       │
    ▼       ▼
Баг на   Обновить
Разраба   ЧТЗ
```

### 6.3 Максимальное количество итераций

Если баг возвращается Разработчику **более 3 раз**, это сигнал о проблеме:
- Аналитик пересматривает ЧТЗ на предмет неоднозначности
- Назначается совместная сессия (Аналитик + Разработчик + Тестировщик)
- Решение документируется

## 7. Артефакты конвейера

### 7.1 Жизненный цикл задачи

```
BUSINESS_TASK_FORM.md          ← Вход: бизнес-задача
        │
        ▼
ЧТЗ документ                    ← Аналитик: требования
        │
        ▼
TASK-XXX-YYY список             ← Аналитик: декомпозиция
        │
        ▼
Исходный код + тесты            ← Разработчик: реализация
        │
        ▼
Test Summary Report             ← Тестировщик: проверка
        │
        ▼
Рекомендация GO/NO-GO           ← Тестировщик: решение
```

### 7.2 Хранение артефактов

| Артефакт | Где хранится | Кто создаёт |
|----------|-------------|-------------|
| Бизнес-задача | `BUSINESS_TASK_FORM.md` | Заказчик |
| ЧТЗ | `требования/ЧТЗ_[Название].md` | Аналитик |
| Декомпозиция | Внутри ЧТЗ, раздел 6 | Аналитик |
| Код | `src/` | Разработчик |
| Тесты | `__tests__/` | Разработчик + Тестировщик |
| Баг-репорты | Внутри Test Summary Report | Тестировщик |
| Test Summary | `TESTING_REPORT_[Name].md` | Тестировщик |

## 8. Правила конвейера (ОБЯЗАТЕЛЬНЫ К СОБЛЮДЕНИЮ)

### 8.1 Правило вопросов

> **Каждая роль ДОЛЖНА задать минимум 3 вопроса перед началом работы.**
>
> Без ответов — работа НЕ начинается.

### 8.2 Правило ЧТЗ

> **Разработчик НЕ пишет код без утверждённого ЧТЗ.**
>
> Если ЧТЗ неоднозначен — Разработчик возвращает Аналитику на доработку.

### 8.3 Правило тестов

> **Разработчик НЕ передаёт работу Тестировщику без прохождения `npm test`.**
>
> Если тесты падают — работа возвращается Разработчику.

### 8.4 Правило приёмки

> **Тестировщик НЕ ставит GO без проверки ВСЕХ критериев приёмки из ЧТЗ.**
>
> Каждый критерий приёмки — минимум один тест-кейс.

### 8.5 Правило регрессии

> **После каждого фикса Тестировщик проверяет не только баг, но и окружающий функционал.**
>
> Regression testing — обязательный этап.

### 8.6 Правило документации

> **Разработчик обновляет документацию (ARCHITECTURE.md, API.md) при изменении архитектуры.**
>
> Тестировщик проверяет актуальность документации.

## 10. Быстрый старт (для Заказчика)

### Чтобы запустить конвейер:

1. **Заполните форму:** `BUSINESS_TASK_FORM.md` — опишите бизнес-задачу
2. **Передайте Аналитику:** Аналитик начнёт с вопросов к вам
3. **Отвечайте на вопросы:** Каждая роль будет задавать вопросы — отвечайте
4. **Утвердите ЧТЗ:** Проверьте требования перед разработкой
5. **Получите результат:** После прохождения всех этапов — готовый продукт

### Что ожидать:

| Этап | Срок | Ваше участие |
|------|------|-------------|
| Аналитик | 1-2 дня | Ответы на вопросы, утверждение ЧТЗ |
| Разработчик | 2-5 дней | Возможно, уточняющие вопросы |
| Тестировщик | 1-2 дня | Приёмка результата |
