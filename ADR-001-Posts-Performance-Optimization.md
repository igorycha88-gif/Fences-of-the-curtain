# ADR-001: Оптимизация производительности и исправление зависания страницы справочника "Столбы"

## Статус
Предложен (2026-04-13)

## Контекст
Страница справочника "Столбы" (`/admin/references/posts`) периодически зависает при первой загрузке.
Количество записей в справочнике: ~20 (небольшое количество).
Ошибок в консоли браузера и логах сервера не наблюдается.

## Анализ проблемы

### Обнаруженные проблемы

#### 1. Критическая ошибка валидации данных (BUG)
**Файл:** `/src/lib/validators/postType.ts`

**Проблема:**
Схема валидации `postTypeBaseSchema` включает поле `pricePerMeter` (строка 19), но это поле отсутствует в модели Prisma `PostType` (`prisma/schema.prisma` строки 92-119).

**Последствия:**
- При сохранении/редактировании столба через API может происходить ошибка валидации
- Серверный валидатор Zod ожидает поле, которого нет в БД
- Это может вызывать проблемы при отправке формы (хотя API route игнорирует это поле)

**Рекомендация:**
Удалить поле `pricePerMeter` из схемы валидации или добавить его в модель Prisma (в зависимости от бизнес-требований).

---

#### 2. Некорректная логика фильтрации в postTypeService.getAll()
**Файл:** `/src/services/admin/postTypeService.ts` (строки 85-94)

**Проблема:**
При фильтрации `validityFilter === 'active'` используется некорректная логика для добавления условия `activeCondition`:

```typescript
where.AND = where.AND ? [...(Array.isArray(where.AND) ? where.AND : [where.AND]), activeCondition] : [activeCondition];
```

**Анализ:**
- Если `where.AND` уже существует и является массивом - добавляем условие корректно
- Если `where.AND` существует, но не является массивом - создаём новый массив
- Если `where.AND` не существует - создаём массив с одним элементом

**Потенциальная проблема:**
При сложных условиях (например, search + validityFilter === 'active') структура `where` может стать некорректной, что может привести к:
- Неожиданным результатам запроса
- Ошибкам Prisma при выполнении запроса
- Медленным запросам из-за неправильного планирования

**Рекомендация:**
Переписать логику фильтрации с использованием Prisma Query Builder или упростить условия.

---

#### 3. Отсутствие мемоизации в компонентах
**Файлы:**
- `/src/components/admin/References/DataTable.tsx`
- `/src/components/admin/References/RelatedMountingHardware.tsx`
- `/src/components/admin/Works/RelatedWorksByReference.tsx`
- `/src/components/admin/References/shared/PriorityColumn.tsx`

**Проблема:**
Компоненты ререндерятся при каждом изменении родительского состояния, даже если их props не изменились.

**DataTable:**
- Функция `renderCell` (строки 82-111) создаётся при каждом рендере
- Колонки с `render` функциями создаются как новые функции при каждом рендере

**PriorityColumn:**
- `handleSubmit` уже мемоизирован через `useCallback`
- Но компонент не мемоизирован полностью

**RelatedMountingHardware и RelatedWorksByReference:**
- Полностью ререндерятся при каждом открытии модального окна
- Нет мемоизации для списка элементов

**Последствия:**
- Лишние ререндеры компонентов
- Уменьшение производительности при большом количестве столбов
- Зависания UI при медленных операциях

**Рекомендация:**
- Мемоизировать функцию `renderCell` через `useCallback`
- Мемоизировать компоненты через `React.memo`
- Использовать `useMemo` для вычисляемых значений

---

#### 4. Отсутствие обработки ошибок в RelatedMountingHardware.fetchRelatedHardware
**Файл:** `/src/components/admin/References/RelatedMountingHardware.tsx` (строки 30-62)

**Проблема:**
Если fetch для монтажной фурнитуры не удаётся или возвращает ошибку 403:
- Компонент не показывает никаких данных (возвращает null или error state)
- Но это не объясняет зависание страницы, так как компоненты рендерятся только в модальном окне

**Потенциальная проблема:**
Если модальное окно открывается при загрузке страницы (по какой-то причине), компоненты могут блокировать рендер.

---

#### 5. Отсутствие кэширования запросов к API
**Файл:** `/src/app/api/admin/post-types/route.ts`

**Проблема:**
API endpoint `/api/admin/post-types` не использует кэширование Redis.
При каждом запросе к странице происходит:
1. Fetch к API
2. Запрос к БД (Promise.all с findMany и count)
3. Обработка результатов

**Последствия:**
- Бессмысленные запросы к БД для одних и тех же данных
- Увеличение нагрузки на БД
- Потенциальные задержки при медленных запросах

**Рекомендация:**
Добавить кэширование результатов запросов в Redis с коротким TTL (например, 60 секунд).

---

#### 6. Отсутствие детального логирования
**Файлы:**
- `/src/app/api/admin/post-types/route.ts`
- `/src/services/admin/postTypeService.ts`

**Проблема:**
При возникновении проблем нет детальных логов для диагностики:
- Нет логов времени выполнения запросов
- Нет логов количества найденных записей
- Нет логов параметров запросов

**Рекомендация:**
Добавить детальное логирование для диагностики производительности:
```typescript
const startTime = Date.now();
console.log(`[POST-TYPES GET] Starting fetch, params: ${JSON.stringify(params)}`);
const result = await postTypeService.getAll(params);
const duration = Date.now() - startTime;
console.log(`[POST-TYPES GET] Completed in ${duration}ms, returned ${result.posts.length} posts`);
```

---

#### 7. Потенциальная проблема с индексами
**Файл:** `prisma/schema.prisma`

**Анализ:**
Модель `PostType` имеет следующие индексы:
- `@@index([active])`
- `@@index([validFrom])`
- `@@index([expirationDate])`
- `@@index([length])`
- `@@index([priority])`
- `@@index([sectionWidth, sectionHeight, wallThickness])`
- `@@index([forMesh])`

**Вывод:**
Индексы присутствуют для всех основных полей фильтрации и сортировки.
При 20 записях проблем с производительностью БД быть не должно.

## Альтернативы

### Альтернатива 1: Использовать React Query вместо fetch
**Преимущества:**
- Встроенное кэширование
- Автоматическая инвалидация
- Оптимистические обновления (optimistic updates)
- Упрощение кода

**Недостатки:**
- Требует внедрения новой библиотеки
- Требует рефакторинга всех fetch запросов

**Вердикт:** Рекомендуется как долгосрочное решение.

---

### Альтернатива 2: Перенести фильтрацию на клиент
**Преимущества:**
- Уменьшение нагрузки на БД
- Быстрый UI

**Недостатки:**
- Увеличение размера передаваемых данных
- Невозможность при большом количестве записей

**Вердикт:** Не рекомендуется для текущего количества записей (~20).

---

## Последствия

### Положительные
1. Устранение критического бага валидации
2. Улучшение производительности страницы "Столбы"
3. Уменьшение количества ререндеров
4. Уменьшение нагрузки на БД благодаря кэшированию
5. Улучшение диагностики проблем через логирование

### Отрицательные
1. Увеличение сложности кода (кэширование, мемоизация)
2. Требуется тестирование изменений

---

1. КРИТИЧЕСКИЙ: Исправить валидацию `pricePerMeter`
2. ВЫСОКИЙ: Исправить логику фильтрации
3. СРЕДНИЙ: Мемоизация компонентов
4. СРЕДНИЙ: Кэширование запросов
5. СРЕДНИЙ: Детальное логирование
