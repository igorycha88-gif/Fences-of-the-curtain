## 2. Цели и задачи

### 2.1 Бизнес-цель
Упростить структуру справочника Лаги для улучшения пользовательского опыта. Перейти от сложной модели с множественными длинами к простой модели с одной фиксированной длиной на номенклатуру. Обеспечить понятные названия полей для конечных пользователей.

### 2.2 Пользовательская ценность
- Упрощение процесса создания и редактирования лаг
- Более понятные названия полей (вместо технических терминов)
- Улучшенная читаемость таблицы справочника
- Возможность видеть цену закупки для администраторов

### 2.3 Ключевые метрики успеха
- Время создания новой лаги сокращается на 40%
- Количество ошибок при заполнении формы снижается на 50%
- Удовлетворенность пользователей UX ≥ 4.5/5

#### 3.1.4 Миграция данных

**User Story 9: Миграция существующих данных**
*Как система, я хочу корректно перенести существующие данные в новую структуру.*

**Acceptance Criteria:**
- Миграция выполняется автоматически при деплое
- Для каждой лаги:
  - Если `availableLengths` содержит элементы:
    - Берется **первая** длина из массива
    - Записывается в новое поле `length`
    - Коэффициент цены (priceCoef) игнорируется
  - Если `availableLengths` пустой или null:
    - Устанавливается длина по умолчанию: 1.0 м
  - Если `purchasePrices` содержит элементы:
    - Берется **первая** цена закупки
    - Записывается в новое поле `purchasePricePerMeter`
  - Если `purchasePrices` пустой или null:
    - Устанавливается null
- После миграции:
  - Поля `availableLengths` и `purchasePrices` (старый формат) удаляются из БД
  - Новые поля `length` и `purchasePricePerMeter` заполнены
- Создается бэкап таблицы LagType перед миграцией
- Rollback скрипт позволяет восстановить старую структуру

**Пример миграции:**

**До:**
```json
{
  "id": "lag-1",
  "name": "Профиль 40x20x2.0",
  "basePricePerMeter": 150,
  "availableLengths": [
    { "length": 2.5, "priceCoef": 1.0 },
    { "length": 3.0, "priceCoef": 1.1 }
  ],
  "purchasePrices": [
    { "length": 2.5, "purchasePrice": 120 },
    { "length": 3.0, "purchasePrice": 145 }
  ]
}
```

**После:**
```json
{
  "id": "lag-1",
  "name": "Профиль 40x20x2.0",
  "basePricePerMeter": 150,
  "length": 2.5,
  "purchasePricePerMeter": 120
}
```

**Примечание:** Берётся первая длина (2.5) и первая цена закупки (120). Если availableLengths пустой, устанавливается длина 1.0 м.

#### 3.1.5 Контроль доступа

**User Story 10: Ограничение доступа к ценам закупки**
*Как система, я хочу скрыть цены закупки от пользователей с ролью MANAGER и CONTENT_MANAGER.*

**Acceptance Criteria:**
- Роль ADMIN:
  - Видит колонку "Цена закупки за единицу" в таблице
  - Может редактировать цену закупки в форме
  - Видит расчет маржи
- Роль MANAGER:
  - **Не видит** колонку "Цена закупки за единицу" в таблице
  - **Не видит** секцию ввода цены закупки в форме
  - Видит только розничную стоимость
- Роль CONTENT_MANAGER:
  - Аналогично MANAGER
- API:
  - GET запросы возвращают поле `purchasePricePerMeter` только для ADMIN
  - POST/PUT запросы с `purchasePricePerMeter` отклоняются для не-ADMIN (403 Forbidden)
  - Логирование попыток несанкционированного доступа

#### 4.2.2 Миграция базы данных

**Migration Script:**
```sql
-- Migration: refactor_lag_type_structure
-- Date: 2026-03-08

BEGIN;

-- Шаг 1: Добавить новые поля
ALTER TABLE "LagType" ADD COLUMN "length" Float;
ALTER TABLE "LagType" ADD COLUMN "purchasePricePerMeter" Float;

-- Шаг 2: Мигрировать данные
UPDATE "LagType"
SET 
  "length" = COALESCE(
    ("availableLengths"::jsonb -> 0 ->> 'length')::float,
    1.0
  ),
  "purchasePricePerMeter" = (
    ("purchasePrices"::jsonb -> 0 ->> 'purchasePrice')::float
  )
WHERE "availableLengths" IS NOT NULL OR "purchasePrices" IS NOT NULL;

-- Шаг 3: Установить длину по умолчанию для записей без availableLengths
UPDATE "LagType"
SET "length" = 1.0
WHERE "length" IS NULL;

-- Шаг 4: Сделать поле length обязательным
ALTER TABLE "LagType" ALTER COLUMN "length" SET NOT NULL;

-- Шаг 5: Удалить старые поля
ALTER TABLE "LagType" DROP COLUMN "availableLengths";
ALTER TABLE "LagType" DROP COLUMN "purchasePrices";

-- Шаг 6: Создать индекс для нового поля
CREATE INDEX "LagType_length_idx" ON "LagType"("length");

COMMIT;
```

**Rollback Script:**
```sql
-- Rollback: refactor_lag_type_structure
-- Date: 2026-03-08

BEGIN;

-- Шаг 1: Восстановить старые поля
ALTER TABLE "LagType" ADD COLUMN "availableLengths" JsonB;
ALTER TABLE "LagType" ADD COLUMN "purchasePrices" JsonB;

-- Шаг 2: Обратная миграция данных (если возможно)
UPDATE "LagType"
SET 
  "availableLengths" = jsonb_build_array(
    jsonb_build_object('length', "length", 'priceCoef', 1.0)
  ),
  "purchasePrices" = CASE 
    WHEN "purchasePricePerMeter" IS NOT NULL 
    THEN jsonb_build_array(
      jsonb_build_object('length', "length", 'purchasePrice', "purchasePricePerMeter")
    )
    ELSE NULL
  END;

-- Шаг 3: Удалить новые поля
ALTER TABLE "LagType" DROP COLUMN "length";
ALTER TABLE "LagType" DROP COLUMN "purchasePricePerMeter";

-- Шаг 4: Удалить индекс
DROP INDEX IF EXISTS "LagType_length_idx";

COMMIT;
```

### 6.3 Обработка ошибок

**Сценарий 1: Не-ADMIN пытается редактировать цену закупки**
- Секция "Цены закупки" скрыта в UI
- При попытке отправить purchasePricePerMeter через API → 403 Forbidden

## 13. Решённые вопросы

### Вопрос 1: Обработка лаг с несколькими длинами ✅ РЕШЕНО
**Решение:** При миграции берём первую длину из массива `availableLengths`.

**Обоснование:** Упрощение структуры требует перехода к одной фиксированной длине на номенклатуру. Пользователи будут уведомлены о необходимости создания отдельных номенклатур для разных длин при необходимости.

---

### Вопрос 2: Значение длины по умолчанию ✅ РЕШЕНО
**Решение:** Если поле `availableLengths` пустое или null, устанавливаем длину 1.0 м по умолчанию.

**Обоснование:** Поле длины является обязательным к заполнению. Значение 1.0 м выбрано как минимально допустимое, чтобы явно показать пользователю, что это значение нужно скорректировать.

---

### Вопрос 3: Обновление калькулятора ✅ РЕШЕНО
**Решение:** Калькулятор заборов **не обновляется** в рамках данного проекта.

**Обоснование:** Калькулятор будет полностью переделан в отдельном проекте в будущем. В данном проекте фокус только на рефакторинге справочника Лаги.

**Примечание:** Это означает, что после деплоя изменений калькулятор может работать некорректно до момента своего обновления. Требуется согласовать с командой поддержки.
