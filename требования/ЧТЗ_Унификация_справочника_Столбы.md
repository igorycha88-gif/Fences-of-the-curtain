## 2. Цели и задачи

### 2.1 Бизнес-цель
Обеспечить полное единообразие структуры данных и пользовательского интерфейса между справочниками Лаги и Столбы для упрощения работы администраторов и снижения поддержки.

### 2.2 Пользовательская ценность
- Единообразный интерфейс между справочниками
- Упрощение обучения новых пользователей
- Сокращение ошибок при работе с разными справочниками
- Понятные названия полей (вместо технических терминов)
- Улучшенная читаемость таблицы справочника
- Возможность видеть цену закупки для администраторов

### 2.3 Ключевые метрики успеха
- Время создания нового столба сокращается на 40%
- Количество ошибок при заполнении формы снижается на 50%
- Консистентность UI 100% между Лагами и Столбами

#### 3.1.3 Миграция данных

**User Story 9: Миграция существующих данных PostType**
*Как система, я хочу корректно перенести существующие данные в новую структуру.*

**Требования:**

| ID | Требование | Обоснование |
|----|------------|-------------|
| REQ-9.1 | Миграция выполняется автоматически при деплое | Автоматизация |
| REQ-9.2 | Для каждого столба: взять первую длину из availableLengths → length | Сохранение данных |
| REQ-9.3 | Если availableLengths пустой → установить длину 1.0 м | Значение по умолчанию |
| REQ-9.4 | Взять первую цену из purchasePrices → purchasePricePerMeter | Сохранение данных |
| REQ-9.5 | Если purchasePrices пустой → установить null | Корректность |
| REQ-9.6 | Удалить поля availableLengths и purchasePrices после миграции | Очистка |
| REQ-9.7 | Создать бэкап таблицы PostType перед миграцией | Безопасность |
| REQ-9.8 | Rollback скрипт для отката изменений | Откат |

#### 4.2.2 Миграция базы данных

**Migration Script:**
```sql
-- Migration: unify_posts_with_lags_structure
-- Date: 2026-03-09

BEGIN;

-- Шаг 1: Добавить новые поля
ALTER TABLE "PostType" ADD COLUMN "length" Float;
ALTER TABLE "PostType" ADD COLUMN "purchasePricePerMeter" Float;

-- Шаг 2: Мигрировать данные
UPDATE "PostType"
SET 
  "length" = COALESCE(
    ("availableLengths"::jsonb -> 0 ->> 'length')::float,
    1.0
  ),
  "purchasePricePerMeter" = (
    ("purchasePrices"::jsonb -> 0 ->> 'purchasePrice')::float
  )
WHERE "availableLengths" IS NOT NULL OR "purchasePrices" IS NOT NULL;

-- Шаг 3: Установить длину по умолчанию для записей без availableLengths
UPDATE "PostType"
SET "length" = 1.0
WHERE "length" IS NULL;

-- Шаг 4: Сделать поле length обязательным
ALTER TABLE "PostType" ALTER COLUMN "length" SET NOT NULL;

-- Шаг 5: Удалить старые поля
ALTER TABLE "PostType" DROP COLUMN "availableLengths";
ALTER TABLE "PostType" DROP COLUMN "purchasePrices";

-- Шаг 6: Создать индекс для нового поля
CREATE INDEX "PostType_length_idx" ON "PostType"("length");

COMMIT;
```

**Rollback Script:**
```sql
-- Rollback: unify_posts_with_lags_structure
-- Date: 2026-03-09

BEGIN;

-- Шаг 1: Восстановить старые поля
ALTER TABLE "PostType" ADD COLUMN "availableLengths" JsonB;
ALTER TABLE "PostType" ADD COLUMN "purchasePrices" JsonB;

-- Шаг 2: Обратная миграция данных (если возможно)
UPDATE "PostType"
SET 
  "availableLengths" = jsonb_build_array(
    jsonb_build_object('length', "length", 'pricePerMeter', "pricePerMeter")
  ),
  "purchasePrices" = CASE 
    WHEN "purchasePricePerMeter" IS NOT NULL 
    THEN jsonb_build_array(
      jsonb_build_object('length', "length", 'purchasePrice', "purchasePricePerMeter")
    )
    ELSE NULL
  END;

-- Шаг 3: Удалить новые поля
ALTER TABLE "PostType" DROP COLUMN "length";
ALTER TABLE "PostType" DROP COLUMN "purchasePricePerMeter";

-- Шаг 4: Удалить индекс
DROP INDEX IF EXISTS "PostType_length_idx";

COMMIT;
```

## 9. Риски и зависимости

### 9.1 Технические риски

**Risk 1: Breaking Changes в структуре данных**

**Category:** Technical  
**Probability:** High  
**Impact:** High

**Description:**
Изменение структуры PostType может сломать существующий код калькулятора и другие компоненты, которые используют availableLengths.

**Potential Impact:**
1. Калькулятор перестанет работать
2. Существующие заказы могут отображаться некорректно
3. Ошибки в API клиентах

**Mitigation Strategies:**
1. **Prevent:** Полный поиск использования availableLengths и purchasePrices в кодовой базе
2. **Mitigate:** Обновить все зависимые компоненты перед деплоем
3. **Accept:** Создать detailed migration plan и протестировать на staging

---

**Risk 2: Потеря данных при миграции**

**Category:** Technical  
**Probability:** Medium  
**Impact:** High

**Description:**
Миграция данных может привести к потере информации о ценах для разных длин.

**Potential Impact:**
1. Если у столба было несколько длин с разными ценами, сохранится только первая
2. Исторические данные о ценах могут быть потеряны

**Mitigation Strategies:**
1. **Prevent:** Создать полный бэкап таблицы PostType перед миграцией
2. **Mitigate:** Протестировать миграцию на копии production данных
3. **Transfer:** Зафиксировать старые данные в архивной таблице

---

### 9.2 Бизнес риски

**Risk 3: Недовольство пользователей изменениями**

**Category:** Business  
**Probability:** Medium  
**Impact:** Medium

**Description:**
Пользователи привыкли к старому интерфейсу и могут негативно отреагировать на изменения.

**Potential Impact:**
1. Увеличение обращений в поддержку
2. Временное снижение продуктивности
3. Негативные отзывы

**Mitigation Strategies:**
1. **Prevent:** Провести обучение пользователей перед релизом
2. **Mitigate:** Создать подробный changelog и гайд по новым полям
3. **Accept:** Подготовить команду поддержки к вопросам

### 10.1 Калькулятор заборов
**Статус:** ⚠️ НЕ ОБНОВЛЯЕТСЯ в данном проекте

**Описание:**
Калькулятор может использовать поле `availableLengths` для расчета стоимости столбов. После деплоя изменений калькулятор может работать некорректно.

- В данном проекте калькулятор НЕ обновляется
