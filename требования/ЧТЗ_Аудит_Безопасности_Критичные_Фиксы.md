# ЧТЗ: Аудит безопасности — критичные исправления

## Контекст
Проведён полный аудит безопасности проекта. Выявлены 6 уязвимостей (2 HIGH, 4 MEDIUM). Проект уже имеет хорошую базу безопасности (NextAuth JWT, RBAC, Zod, bcrypt, rate limiting, CSP, HSTS). Исправляем только реальные проблемы.

## Маршрут: Аналитик → Разработчик → Тестировщик → DevOps

## Задачи

### TASK-SEC-01: SVG XSS — санитизация SVG из БД (HIGH)
**Проблема:** `TrussDrawing.tsx:15` и `SavedCalculations.tsx:259` рендерят SVG из базы данных через `dangerouslySetInnerHTML` без санитизации. Если SVG содержит `<script>` или event handlers — выполнится код в контексте админа.

**Файлы:**
- `src/components/admin/TrussCalculator/TrussDrawing.tsx`
- `src/components/admin/TrussCalculator/SavedCalculations.tsx`
- `src/lib/sanitize.ts` (добавить `sanitizeSvg`)

**Решение:**
1. Добавить функцию `sanitizeSvg(html: string): string` в `src/lib/sanitize.ts` — использует DOMPurify с `ALLOWED_TAGS` для SVG-элементов (`svg`, `path`, `line`, `circle`, `rect`, `text`, `g`, `polyline`, `polygon`, `defs`, `marker`, `title`, `desc`, `tspan`, `linearGradient`, `stop`) и `ALLOWED_ATTR` для SVG-атрибутов. Запретить `on*` атрибуты и `<script>`.
2. В `TrussDrawing.tsx:15` обернуть `svgString` через `sanitizeSvg(svgString)`
3. В `SavedCalculations.tsx:259` обернуть `calc.svgDrawing` через `sanitizeSvg(calc.svgDrawing)`

**Критерии приёмки:**
- SVG с `<script>alert(1)</script>` — скрипт удалён, остальной SVG отображается
- SVG с `onload="alert(1)"` — атрибут удалён
- Нормальный SVG-чертёж фермы отображается без искажений

### TASK-SEC-02: Утечка error.message в API-ответах (HIGH)
**Проблема:** 247+ случаев передачи `error.message` в JSON-ответах API. Prisma ошибки (P2002, P2025) содержат имена таблиц, полей, connection string. В production это раскрывает внутреннюю структуру БД.

**Файлы:** ~40 route файлов в `src/app/api/`

**Решение:**
1. Создать helper `safeErrorResponse(error: unknown, context?: string)` в `src/lib/api-error.ts`:
   - В production: `{ error: 'Internal server error' }` с status 500
   - В development: `{ error: error.message }` (как сейчас для отладки)
   - Для известных бизнес-ошибок (строковые коды типа `'ESTIMATE_NOT_FOUND'`) — пробрасывать как есть
2. Заменить catch-блоки в **публичных** API routes (`/api/orders`, `/api/calculator/*`, `/api/contact`):
   - Заменить `{ error: error.message }` → `safeErrorResponse(error)`
3. В **admin** API routes: оставить текущую логику для бизнес-ошибок (они проверяют `error.message` на известные строки), но для fallback catch-all (status 500) использовать `safeErrorResponse`

**Критерии приёмки:**
- В production: при Prisma ошибке клиент видит `{ "error": "Internal server error" }`
- В development: `{ "error": "полный текст ошибки" }` (для отладки)
- Бизнес-ошибки (`ESTIMATE_NOT_FOUND`, `'не найден'`, `'уже существует'`) продолжают работать корректно

### TASK-SEC-03: Защита /api/metrics авторизацией (HIGH)
**Проблема:** `/api/metrics` — Prometheus метрики без авторизации. Доступны любому, раскрывают производительность, request rates, error rates.

**Файл:** `src/app/api/metrics/route.ts`

**Решение:**
1. Добавить проверку: если `NODE_ENV === 'production'` — требовать Basic Auth через env-переменную `METRICS_BEARER_TOKEN` или ограничить по заголовку `Authorization: Bearer <METRICS_TOKEN>`
2. Если токен не задан — в production вернуть 404 (endpont недоступен)
3. В development — оставить как есть (без авторизации)

**Критерии приёмки:**
- `GET /api/metrics` в production без токена → 401 или 404
- `GET /api/metrics` в development → работает как раньше
- Prometheus scrape конфиг обновлён (передать токен через env)

### TASK-SEC-04: Защита GET /api/analytics/events (MEDIUM)
**Проблема:** GET `/api/analytics/events` возвращает дневную аналитику (page_view, contact_form_submit) без авторизации.

**Файл:** `src/app/api/analytics/events/route.ts`

**Решение:**
1. Добавить `requireAdmin()` для GET-метода
2. POST-метод оставить публичным (он принимает события от клиентов)

**Критерии приёмки:**
- `GET /api/analytics/events` без авторизации → 401
- `POST /api/analytics/events` — работает как раньше

### TASK-SEC-05: Rate limiting + валидация sessionId в Analytics (MEDIUM)
**Проблема:** POST `/api/analytics/events` не имеет rate limiting — атакующий может заполнить Redis мусорными данными. `sessionId` используется без санитизации как ключ Redis.

**Файл:** `src/app/api/analytics/events/route.ts`

**Решение:**
1. Добавить валидацию `sessionId` — regex `/^[a-zA-Z0-9-]+$/`, длина 1-64 символа. Некорректный → 400
2. Добавить валидацию `eventName` — regex `/^[a-zA-Z0-9_]+$/`, длина 1-64 символа
3. Добавить rate limit: 100 запросов/минута по IP (используя существующий `rate-limit.ts`)

**Критерии приёмки:**
- `sessionId` с спецсимволами (включая `:`) → 400
- `eventName` с спецсимволами → 400
- Более 100 запросов/мин → 429
- Нормальные запросы проходят

### TASK-SEC-06: Удаление fallback-секретов из docker-compose.yml (MEDIUM)
**Проблема:** `docker-compose.yml` содержит слабые дефолты: `NEXTAUTH_SECRET:-dev-secret-change-me`, `CRON_SECRET:-dev-cron-secret`, `POSTGRES_PASSWORD:-postgres`. Если env не задан — production работает с weak секретами.

**Файл:** `docker-compose.yml`

**Решение:**
1. Убрать дефолтные значения для критичных переменных — оставить только `${VAR}` (без `:-default`)
2. Для `NEXTAUTH_SECRET`, `CRON_SECRET`, `POSTGRES_PASSWORD`, `REDIS_PASSWORD`, `SMTP_PASS` — если переменная не задана, контейнер должен упасть (fail-fast)
3. Для необязательных переменных (TELEGRAM, RECAPTCHA) — оставить пустой дефолт `:-`

**Критерии приёмки:**
- `NEXTAUTH_SECRET` не задан → контейнер не стартует (env validation)
- Все критичные секреты обязательны
