# ЧТЗ_Промпт_для_аналитика

Название проекта: Управление приоритетами номенклатуры в справочниках

1) Контекст и цель
- Контекст: во всех справочниках, где ведётся учёт номенклатуры, добавить системное поле Приоритет для каждой номенклатуры.
- Цель: обеспечить автоматическую нумерацию приоритетов, уникальность внутри справочника, автоматическую перестройку порядка при изменении приоритетов и корректное отображение приоритета в карточке номенклатуры, а не в списке справочника.

2) Термины
- Справочник: набор номенклатур, принадлежащий конкретному справочнику/категории.
- Номенклатура: элемент справочника, в типовом случае имеет поля: идентификатор, код, наименование, и новый системный параметр Приоритет.
- Приоритет: числовое значение, определяющее порядок представления номенклатуры в справочнике. Наименьшее значение (1) считается самым высоким приоритетом.

3) Функциональные требования (FR)

FR-1. Добавление приоритета во все справочники
- При добавлении новой номенклатуры во все справочники автоматически устанавливается значение Приоритет.
- Значение Приоритет формируется как: если в справочнике ещё нет элементов, Приоритет = 1; иначе Приоритет = максимальное значение Приоритет уже существующих элементов в этом справочнике + 1.

FR-2. Автоматическая проставка приоритета
- При добавлении новая номенклатура получает порядковый номер, который не требует ручного ввода со стороны пользователя.
- Список номеклатур внутри справочника сортируется по Приоритету возрастанию (1, 2, 3, ...).

FR-3. Уникальность приоритета внутри справочника
- В рамках одного справочника значения Приоритет должны быть уникальными.
- Попытка добавить или закрепить повторяющийся Приоритет приводит к ошибке в пользовательском интерфейсе (сообщение: “Приоритет занят. Используйте доступное значение, или разрешите автоматическую перестройку очередности.”).
- Исключение: При этом добавление через автоматическую перегруппировку не нарушает целостность – система предотвращает дублирующий приоритет и корректно перераспределяет значения.

FR-4. Изменение приоритета номенклатуры
- Если пользователь хочет изменить Приоритет существующей номенклатуры на значение P:
  - если на позиции P уже есть другая номенклатура, она должна быть переведена на следующий доступный приоритет (P+1), и так далее, до освобождения позиции P.
- Операция перестройки должна быть атомарной: если в ходе операцию что-либо нарушится, транзакция откатывается.
- В результате новая номенклатура получает Приоритет P, а все затронутые элементы получают соответствующие перестановки (каскадная перестановка без пропусков).

FR-5. Сортировка и отображение
- В списке справочника номенклатура сортируется по Приоритету начиная с 1.
- В таблице справочника не отображается столбец Приоритет (он скрыт для списка).
- Приоритет отображается только в карточке номенклатуры (детальная страница).

FR-6. Удаление и перестройка
- При удалении номенклатуры её Приоритет освобождается, и остальные элементы справочника должны быть автоматически перестроены так, чтобы не было пропусков (последовательность 1..N).

FR-7. Константы и ограничения
- Приоритет хранится как integer, не может быть null.
- Уникальность приоритета внутри конкретного справочника обеспечивается на уровне бизнес-логики и/или БД (через уникальный индекс в сочетании (reference_id, priority)).

FR-8. Миграции данных
- Для существующих данных внедрить миграцию: присвоить всем элементам корректные Приоритеты в соответствии с текущим порядком представления (если такие данные есть) или выровнять по порядку добавления.
- Обеспечить обратную совместимость и минимальное нарушение доступности системы во время миграции.

4) Нефункциональные требования (NFR)

NFR-1. Производительность
- Обновление порядка при изменении Приоритета должно быть линейным по числу элементов, оптимально через пакетные операции/транзакции.

NFR-2. Безопасность и контроль доступа
- Изменение Приоритета допускается только для пользователей с соответствующими правами администрирования справочников.

NFR-3. Надёжность и трассируемость
- Все изменения Приоритетов должны попадать в журнал аудита (когда, кем, какое изменение).

NFR-4. Миграции и откаты
- Миграции должны быть опробованы на тестовом окружении и иметь возможность отката без потери данных.

5) Архитектурно-данные изменения (пример)

- База данных:
  - Добавить поле: Nomenclature.priority INT NOT NULL DEFAULT 0
  - Добавить уникальный индекс (reference_id, priority)
- Модель/Слой бизнес-логики:
  - Логика присвоения нового приоритета на создание: max(priority) + 1.
  - Логика перестановки при изменении priority: каскадная перестановка без пропусков.
  - Логика перерасчёта после удаления: перенумерация оставшихся элементов.
- API/UI:
  - Эндпоинт на создание номенклатуры: приоритет не запрашивается, устанавливается автоматически.
  - Эндпоинт на обновление номенклатуры: поддержка изменения priority с каскадом.
  - UI: список скрывает столбец Приоритет; карточка отображает Приоритет.
  - Сообщения об ошибках и уведомлениях при конфликте приоритета.

6) Правила валидации и UX
- Валидировать входящие данные при обновлении priority; при некорректных данных возвращать понятную ошибку.
- При каскадной перестановке показывать пользователю итоговый порядок и лог изменений.
- Приоритеты должны быть последовательны без пропусков после каждого шага.

7) План тестирования (Acceptance Criteria)
- AC1: При добавлении первой номенклатуры в справочник Приоритет = 1; следующей — 2 и т.д.
- AC2: При попытке добавить номенклатуру с повторяющимся Приоритетом через UI, система выдаёт ошибку и не допускает создание.
- AC3: При изменении приоритета на занятое место выполняется каскадная перестановка: занятое место освобождается (перестановка вниз).
- AC4: После удаления элемент перестраивает приоритеты у оставшихся так, чтобы не было пропусков (1..N).
- AC5: В списке справочника элементы сортируются по Приоритету; столбец Приоритет не показывается в списке; в карточке отображается текущий Приоритет.
- AC6: Все изменения приоритетов записываются в журнал аудита.
- AC7: Миграции выполняются без потери данных и поддерживают откат.

8) Риски
- Конкурентные обновления: необходима транзакционность и блокировка на уровне справочника.
- Миграции большого объёма данных: планировать поэтапно и мониторинг.
- Непреднамеренная смена порядка пользователями: внедрить уведомления и проверки.

9) Терминология и бизнес-правила
- Номенклатуры внутри справочника упорядочиваются строго по Приоритету, начиная с 1.
- Приоритет не отображается в списке; доступен в карточке.
- Изменение приоритета инициируется через карточку номенклатуры; система выполняет каскадную перестановку.
