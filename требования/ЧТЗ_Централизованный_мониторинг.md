## 1. Цели и задачи

### 1.1 Бизнес-цель
Подключить zabor-i-naves.ru к централизованному мониторингу (VPS 130.49.129.241):
видеть в общих дашбордах доступность сайта, бизнес-метрики (посетители/заявки/
конверсия), метрики приложения, сервера и PostgreSQL — без открытия новых портов.

### 1.2 Пользовательская ценность
Владелец в единой Grafana мониторинга видит zabor-i-naves.ru рядом с
da-dryclean.ru и эвакуация.online: дашборды «Обзор сайта», «Все сайты»,
«Бизнес сайта»; алерты SiteDown / SiteNoTraffic / SiteSslExpiringSoon приходят
в общий Telegram.

### 1.3 Метрики успеха
- 4 эндпоинта метрик отвечают 200 по ключу `X-Monitoring-Key`;
- без ключа — 403; новые порты наружу не открываются;
- тег Яндекс.Метрики 108488683 установлен на сайте (сейчас отсутствует);
- после подключения: `monitoring_site_metrics_up{site="zabor-i-naves.ru",kind=...}=1`.

## 2. Что требуется от владельца (доступы и решения)

### Блок А — Яндекс.Метрика (данные о визитах)
1. **Установить тег счётчика на сайт.** Счётчик `108488683` прописан в `.env`
   (`NEXT_PUBLIC_YANDEX_METRIKA_ID=108488683`), CSP уже разрешает `mc.yandex.ru`,
   **но тег на живом сайте не рендерится** (проверено 2026-08-24: в HTML и JS-чанках
   отсутствует). Без тега Метрика будет показывать 0 визитов.
   → Команде сайта: проверить компонент подключения Метрики (рендер тега,
   флаги окружения на проде).
2. **Выдать мониторингу доступ к счётчику 108488683.** Текущий токен мониторинга
   получает 403 (счётчик в другом аккаунте Яндекса). Варианты (на выбор владельца):
   - в Метрике: Настройки счётчика → Доступы → добавить аккаунт-представитель
     мониторинга (аккаунт сообщит исполнитель мониторинга); или
   - выпустить OAuth-токен с правом `metrika:read` из аккаунта-владельца счётчика
     и передать защищённым каналом (не в чат/git).

### Блок Б — Яндекс.Вебмастер (поисковые запросы, позиции)
1. Сайт уже верифицирован метатегом `b82b0cfe086d3936` — подтверждение прав НЕ требуется.
2. **Выдать OAuth-токен** с правом `webmaster:read` (или `Просмотр данных
   Вебмастера`) из аккаунта Яндекса, где добавлен сайт:
   https://oauth.yandex.ru → создать токен → передать защищённым каналом.
   По токену мониторинг сам определит `host_id` и начнёт собирать поисковые
   запросы (топ-50, динамика по дням).

### Блок В — Эндпоинты метрик сайта (см. §3–5)
Выполняется командой сайта. Ключ `X-Monitoring-Key` (64 hex, персайтный)
генерируется мониторингом и передаётся владельцем команде сайта защищённым
каналом. Ключ НЕ попадает в git, коммиты, логи, ЧТЗ.

## 3. Контракт взаимодействия (ADR-007 мониторинга, обязательно)

| Параметр | Значение |
|---|---|
| Пути | `GET https://zabor-i-naves.ru/metrics/{tracking,content,node,postgres}` |
| Auth | Заголовок `X-Monitoring-Key: <64 hex>`; неверный/отсутствующий → **403** |
| Методы | Только `GET` (иначе 403/405) |
| Rate limit | 10 r/s на location'ы `/metrics/` |
| Формат | Prometheus text exposition, `Content-Type: text/plain; version=0.0.4` |
| Канал | Только публичный HTTPS (443). Новых открытых портов НЕТ |

До готовности ответы 404 — норма (мониторинг подключён с «полным пакетом» и
будет показывать `up=0` + warning-алерт до реализации эндпоинтов).

## 4. Спецификация метрик

### 4.1 `business_*` — kind=tracking (гейджи, окна 24ч/1ч, пересчёт раз в 60 с, кэш в памяти)

Источники: собственная аналитика сайта (события в Redis: `/api/analytics/events`,
sessionId в cookie `analytics_session_id`) + Prisma-модель `Order` (заявки).

| Метрика | Источник данных |
|---|---|
| `business_sessions_active` | активные сессии за последние 30 мин (Redis) |
| `business_page_views_24h`, `business_page_views_1h` | просмотры за окно (Redis/аналитика) |
| `business_unique_visitors_24h` | COUNT(DISTINCT session/ip) за 24ч |
| `business_sessions_24h` | сессии за 24ч (логика сайта 30-мин окном) |
| `business_avg_session_duration_seconds_24h` | средняя длительность сессии |
| `business_bounce_rate_24h` | доля однократных просмотров (0..1) |
| `business_events_24h{event_type}` | события аналитики, ≤ 20 значений лейбла |
| `business_leads_24h`, `business_leads_1h` | заявки (Order, все статусы) |
| `business_conversion_rate_24h` | leads_24h / sessions_24h (деление на 0 → 0) |
| `business_service_clicks_24h{service}` | клики по услугам/типам заборов и навесов, топ-20 + `other` |
| `business_referral_sources_24h{source}` | только если фиксируется referer, топ-10 + `other` |
| `business_geo_visitors_24h{city}` | только если есть гео-данные, топ-10 + `other` |

Правила:
- Метрики без данных (referer/geo не фиксируются) — не отдаются вообще (не нули).
- Кардинальность: `event_type` ≤ 20, `service` ≤ 21, `city` ≤ 11.
- Redis/PostgreSQL-запросы — с учётом памяти/индексов, без полного перебора
  больших коллекций (использовать счётчики Redis, TTL-структуры за окно).

### 4.2 `content_*` — kind=content (метрики приложения)
На сайте УЖЕ есть `src/lib/http-metrics.ts` и публичный `GET /api/metrics`
(normalized paths, timing buckets). Требуется:
- переиспользовать существующую реализацию как источник kind=content;
- **закрыть доступ ключом** (см. §6 Безопасность — сейчас эндпоинт открыт);
- имена привести к контракту: `content_http_requests_total{method,route,code}`
  (counter), `content_http_request_duration_seconds{method,route}` (histogram);
  `route` — нормализованный шаблон (`/services/:slug`), ≤ 100 значений;
  пути `/metrics/*` в метрики приложения не включать.

### 4.3 kind=node (серверные метрики)
- node_exporter ≥ 1.x, systemd-сервис, слушает **только 127.0.0.1:9100**;
- не контейнер (паттерн эталона), collector'ы по умолчанию.

### 4.4 kind=postgres (метрики PostgreSQL)
- postgres_exporter, Docker-контейнер в compose сайта, слушает **только 127.0.0.1:9187**;
- отдельный readonly-пользователь БД с ролью `pg_monitor` (НЕ суперпользователь);
- DSN — только в `.env` сайта (chmod 600), не в compose/git.

> Redis-метрики в контракт не входят (4 kind фиксированы ADR-010); здоровье Redis
> уже видно через `/api/health` сайта и может быть отражено в `business_*`
> на усмотрение команды.

## 5. Инфраструктура (nginx сайта)

1. `/etc/nginx/conf.d/monitoring-key.conf` (chmod 600, владелец root):
   ```nginx
   map $http_x_monitoring_key $metrics_auth { default 0; "<КЛЮЧ>" 1; }
   ```
2. В server-блоке сайта (443):
   ```nginx
   limit_req_zone $binary_remote_addr zone=metrics_limit:10m rate=10r/s;

   location ^~ /metrics/tracking {
     limit_except GET { deny all; }
     if ($metrics_auth = 0) { return 403; }
     limit_req zone=metrics_limit burst=5 nodelay;
     proxy_pass http://<upstream приложения>/api/metrics/tracking;
   }
   # аналогично: /metrics/content → <upstream приложения> (/api/metrics)
   #              /metrics/node     → http://127.0.0.1:9100
   #              /metrics/postgres → http://127.0.0.1:9187
   ```
3. Проксировать через **именованный upstream** приложения (тот же, что использует
   сайт), чтобы деплой не ломал эндпоинты.
4. Ключ не добавлять в log_format; access_log `/metrics/` — отдельный файл,
   минимальный формат.
5. `nginx -t` → reload; проверить, что сайт и `/api/health` работают.

## 6. Безопасность

- **Сейчас `GET /api/metrics` открыт без авторизации** (проверено 2026-08-24,
  200 без ключа) — команда сайта должна закрыть его (ключ по §5 или иным
  способом) одновременно с внедрением контракта.
- Ключ только в `monitoring-key.conf` (600) и при необходимости в `.env`
  приложения; не в git/логах/документах.
- Порты 9100/9187 — только 127.0.0.1; наружу ничего не открывается.
- Токены Яндекса (Блоки А/Б) передаются владельцем защищённым каналом;
  в чат, git, ЧТЗ не фиксируются.

## 7. Нефункциональные требования

- Пересчёт гейджей не чаще 1 раза в 60 с (кэш); Prometheus скрейпит раз в
  15–60 с — нагрузка минимальна.
- Формат Prometheus text 0.0.4; имена метрик — точно как в §4 (центральные
  дашборды и алерт `SiteNoTraffic` используют `business_page_views_24h`).

## 8. Декомпозиция на задачи (команда сайта)

### Backend
- **TASK-BCK-001** Route `/api/metrics/tracking`: `business_*` гейджи из
  Redis-аналитики + Prisma `Order`, кэш 60 с, окна 24ч/1ч, топ-N+`other`. ~4 ч
- **TASK-BCK-002** **Закрытие `/api/metrics`** (требование владельца
  мониторинга, v1.2): метрики приложения отдаются наружу ТОЛЬКО по ключу
  `X-Monitoring-Key`. Открытый `GET /api/metrics` → 403. Реализация на nginx
  (§5, тот же map `$metrics_auth`) или в приложении. ~1 ч
### Testing
- **TASK-TST-001** Vitest: расчёт гейджей (happy path, пустые данные → нули,
  окна, кардинальность, деление на 0). ~2 ч
- **TASK-TST-002** Контракт: 200 с ключом / 403 без / не-GET, формат text/plain. ~1 ч
### Infrastructure
- **TASK-INF-001** Установка тега Метрики 108488683 (проверить рендер на проде). ~0.5 ч
- **TASK-INF-002** node_exporter (systemd, 127.0.0.1:9100). ~1 ч
- **TASK-INF-003** postgres_exporter (docker, 127.0.0.1:9187, pg_monitor). ~1.5 ч
- **TASK-INF-004** nginx: key-map, 4 location, rate limit, upstream, reload. ~1.5 ч

Порядок: BCK → TST → INF; выкатка на прод — штатным деплоем сайта.

## 9. Критерии приёмки

1. `curl -H "X-Monitoring-Key: <ключ>" https://zabor-i-naves.ru/metrics/tracking`
   → 200, `text/plain`, содержит `business_page_views_24h` и `business_leads_24h`.
2. Без ключа/с неверным ключом → 403 на всех 4 путях; `POST` → 403/405.
3. `GET /api/metrics` без ключа → 403 (закрыт).
4. `/metrics/node` отдаёт `node_*`, `/metrics/postgres` отдаёт `pg_*`,
   `/metrics/content` отдаёт `content_http_requests_total`.
5. `ss -tlnp`: 9100 и 9187 слушают только 127.0.0.1.
6. Тег Метрики: `curl -s https://zabor-i-naves.ru | grep -c mc.yandex` ≥ 1;
   в Метрике через ~30 мин появляются визиты.
7. Тесты/линты проекта — зелёные.
8. Регрессия: сайт 200, `/api/health` ok, админка работает после правок nginx.
9. (После подключения мониторингом) `monitoring_site_metrics_up{site="zabor-i-naves.ru"}=1`
   для всех 4 kind; данные на дашборде «Бизнес сайта».

## 10. Риски и зависимости

- Тег Метрики не рендерится (возможно, отключён флагом на проде) → без него
  визиты = 0 при валидном токене.
- Токен Метрики мониторинга не имеет доступа к счётчику (403) → до выдачи
  доступа (Блок А.2) сбор визитов невозможен.
- Хост Вебмастера не в аккаунтах мониторинга → до токена (Блок Б) поиск не
  собирается.
- Данные аналитики в Redis без TTL/окон → считать окна по счётчикам с TTL,
  не перебором ключей.

## Дополнение v1.2 (2026-08-24): `/api/metrics` — только по ключу (требование владельца)

1. **Требование:** метрики приложения НЕ отдаются в открытом виде. Сейчас
   `GET /api/metrics` отвечает 200 без авторизации любому посетителю
   (проверено 2026-08-24) — это утечка телеметрии (трафик, события,
   длительность запросов, top_fence_types и т.п.).
2. **Целевое состояние:**
   - `GET /api/metrics` без ключа или с неверным `X-Monitoring-Key` → **403**;
   - с корректным ключом → 200 (формат не меняется);
   - наружу для мониторинга — только через `/metrics/content` (§5, тот же ключ).
3. **Реализация (на выбор команды сайта):**
   - nginx: в существующий server-блок добавить
     `location = /api/metrics { if ($metrics_auth = 0) { return 403; } proxy_pass http://<upstream>/api/metrics; }`
     (map `$metrics_auth` уже создаётся по §5.1);
   - или проверка ключа в самом route handler `/api/metrics`.
4. **Внутренние потребители** (собственный Prometheus/Grafana сайта, если
   скрейпят через nginx) — добавить заголовок `X-Monitoring-Key` в scrape-конфиг
   или скрейпить приложение напрямую на localhost (тогда наружу эндпоинт всё
   равно закрыт).
5. Критерий приёмки — §9 п.3: `curl https://zabor-i-naves.ru/api/metrics` → 403.
