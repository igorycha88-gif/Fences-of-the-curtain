## 1. Цели и задачи

### 1.1 Бизнес-цель
Устранить критическое замедление работы калькулятора после внедрения Rate Limiting:
- **Загрузка типов заборов**: сократить с ~4 сек до <500 мс
- **Расчёт калькулятора**: сократить с ~10+ сек до <2 сек

### 1.2 Пользовательская ценность
- Улучшение UX: мгновенный отклик калькулятора
- Снижение отказов пользователей из-за медленной работы
- Повышение конверсии заявок

### 1.3 Метрики успеха
| Метрика | AS-IS | TO-BE | Измерение |
|---------|-------|-------|-----------|
| Загрузка типов заборов | ~4000 мс | <500 мс | P95 latency API /api/calculator/fence-types |
| Расчёт калькулятора | ~10000+ мс | <2000 мс | P95 latency API /api/calculator/fence/estimate |
| Количество DB запросов при расчёте | 10-15 | 2-4 | APM/логирование |
| Внешние HTTP запросы | 1 (ip-api.com) | 0 (async) | APM/логирование |

## 2. Диагностика проблем

### 2.1 Анализ текущего состояния

#### 2.1.1 Загрузка типов заборов (fence-types)

**Текущий код** (`src/services/calculator/fenceTypeCalculatorService.ts`):
```
GET /api/calculator/fence-types
    │
    ├─► Redis GET (5-50 мс)
    │   └─► Если MISS:
    │       └─► PostgreSQL SELECT fenceType (50-200 мс)
    │           └─► Redis SET (5-50 мс)
    │
    └─► Response: Cache-Control: no-store ❌  ← ГЛАВНАЯ ПРИЧИНА 4 СЕК
```

**⚠️ КРИТИЧЕСКИЙ БАГ #1 — `fence-types/route.ts` активно отключает кеш:**
```typescript
// src/app/api/calculator/fence-types/route.ts (строка 19)
headers: {
  'Cache-Control': 'no-store, no-cache, must-revalidate, proxy-revalidate', // ❌
  'Pragma': 'no-cache',
  'Expires': '0',
}
```
Несмотря на то что `fenceTypeCalculatorService` кеширует данные в Redis (TTL=300s),
этот заголовок **запрещает браузеру и CDN хранить ответ**. При каждом переходе между
страницами браузер делает свежий HTTP-запрос → Redis hit → но ответ всё равно
занимает 100-500мс на каждый переход. При cold start Redis это 4000мс.

**⚠️ КРИТИЧЕСКИЙ БАГ #2 — Redis в production не переиспользует соединение:**
```typescript
// src/lib/redis.ts (строка 17)
if (process.env.NODE_ENV !== 'production') globalForRedis.redis = redis; // ❌
```
В production каждый cold start создаёт новое TCP-соединение к Redis (+100-500мс).
После внедрения Rate Limiting появился второй Redis-клиент (`rate-limit.ts` тоже
импортирует redis), что удвоило задержку cold start.

**Все проблемы:**
1. ❌ **Критический**: `Cache-Control: no-store` в route.ts отменяет HTTP-кеширование
2. ❌ **Критический**: Redis connection не переиспользуется в production
3. При cold start Redis connection = +100-500 мс (усилено после Rate Limiting)
4. Нет warmup кеша при старте приложения

**⚠️ КРИТИЧЕСКИЙ БАГ #3 — getCityByIP блокирует ответ (fenceEstimateService.ts:329):**
```typescript
// Строка 329 — БЛОКИРУЕТ весь расчёт до 3000мс
city = await getCityByIP(metadata.ipAddress);

// Строка 333 — ждёт city перед созданием

```
Нельзя просто убрать `await` — `city` передаётся в `create`. Требуется **структурное
изменение**: создать estimate без города → вернуть ответ → обновить город фоново.

**Все проблемы:**
1. **Последовательные запросы**: большинство DB запросов выполняются последовательно

2. **Отсутствие кеширования**: справочные данные не кешируются
3. **❌ Блокирующий IP lookup**: вызывается ДО сохранения estimate, блокирует до 3000 мс
4. **N+1 запросы**: mountingHardware запрашивается 3 раза для разных типов
5. **Fallback логика**: при отсутствии работ для ворот/калитки — дополнительный запрос

## 3. Функциональные требования

### 3.1 User Stories с Acceptance Criteria

#### US-001: Кеширование справочных данных калькулятора
**Как** система калькулятора,  
**Я хочу** кешировать справочные данные в Redis с TTL,  
**Чтобы** избежать повторных запросов к БД для статичных данных.

**Acceptance Criteria:**
```
Given справочные данные (столбы, лаги, профнастил, работы, монтажная фурнитура)
When выполняется запрос к калькулятору
Then данные запрашиваются из Redis
And при MISS данные загружаются из БД и кешируются
And TTL кеша = 300 секунд (5 минут)
And инвалидация кеша при изменении справочников в админке
```

**Охватываемые сервисы:**
- postCalculator
- lagCalculator
- profnastilCalculator
- gateLookup
- wicketLookup
- workService (методы для калькулятора)
- mountingHardwareCalculator

---

#### US-002: Параллельные запросы к БД
**Как** система калькулятора,  
**Я хочу** выполнять независимые запросы к БД параллельно,  
**Чтобы** сократить общее время расчёта.

**Acceptance Criteria:**
```
Given расчёт калькулятора с воротами и калиткой
When выполняются запросы к справочникам
Then независимые запросы выполняются параллельно через Promise.all
And последовательными остаются только зависимые запросы
And время расчёта сокращается на 50-70%
```

**Схема TO-BE:**
```
POST /api/calculator/fence/estimate
    │
    ├─► [Parallel Block 1]
    │   ├─► prisma.fenceType.findUnique
    │   ├─► Redis: get cached posts/lags/profnastil
    │   └─► Redis: get cached works
    │
    ├─► [Parallel Block 2] (если hasGate)
    │   ├─► findGateByTypeAndLength (from cache)
    │   └─► getWorksForCalculatorByReference (from cache)
    │
    ├─► [Parallel Block 3] (если hasWicket)
    │   ├─► findWicketByHeightAndWidth (from cache)
    │   └─► getWorksForCalculatorByReference (from cache)
    │
    ├─► [Parallel Block 4]
    │   ├─► calculatePosts (from cache)
    │   ├─► calculateLags (from cache)
    │   └─► calculateProfnastil (from cache)
    │
    ├─► [Parallel Block 5]
    │   └─► calculateMountingHardware (from cache, single query)
    │
    ├─► [Async] getCityByIP (не блокирует ответ)
    │
    └─► prisma.fenceEstimate.create
```

**Как** система калькулятора,  
**Я хочу** выполнять определение города асинхронно,

```
Given запрос на расчёт калькулятора

```

## 4. Нефункциональные требования

### 4.1 Производительность

| Метрика | Целевое значение | Метод измерения |
|---------|------------------|-----------------|
| P50 latency fence-types | <100 мс | APM/логи |
| P95 latency fence-types | <500 мс | APM/логи |
| P50 latency fence/estimate | <500 мс | APM/логи |
| P95 latency fence/estimate | <2000 мс | APM/логи |
| Cache hit rate | >95% | Redis metrics |
| DB connections per request | <5 | Prisma metrics |

### 4.2 Надёжность

- **Graceful degradation**: при недоступности Redis запросы идут напрямую в БД
- **Circuit breaker**: при недоступности IP API - пропускать без города
- **Fallback**: при ошибке кеша - данные из БД

### 4.3 Масштабируемость

- **Memory**: кеш в Redis не должен превышать 100MB
- **TTL**: автоматическая очистка устаревших ключей
- **Invalidation**: при обновлении справочников в админке

#### 5.3.2 Оптимизированный fenceEstimateService

```typescript
// Псевдокод оптимизированного calculateFenceEstimate

export async function calculateFenceEstimate(
  input: FenceEstimateInput,
  metadata?: CalculationMetadata
): Promise<FenceEstimateResult> {
  
  // 1. Параллельная загрузка базовых данных (из кеша)
  const [fenceType, posts, lags, profnastil, gateWorks, wicketWorks] = await Promise.all([
    prisma.fenceType.findUnique({ where: { id: input.fenceTypeId } }),
    cache.getOrSet(CACHE_KEYS.POSTS_ACTIVE, () => fetchActivePosts(), TTL),
    cache.getOrSet(CACHE_KEYS.LAGS_ACTIVE, () => fetchActiveLags(), TTL),
    cache.getOrSet(CACHE_KEYS.PROFNASTIL_ACTIVE, () => fetchActiveProfnastil(), TTL),
    input.hasGate 
      ? cache.getOrSet(CACHE_KEYS.WORKS_BY_REFERENCE('GATE', gateId), () => fetchWorks('GATE', gateId), TTL)
      : Promise.resolve([]),
    input.hasWicket
      ? cache.getOrSet(CACHE_KEYS.WORKS_BY_REFERENCE('WICKET', wicketId), () => fetchWorks('WICKET', wicketId), TTL)
      : Promise.resolve([]),
  ]);
  
  // 2. Расчёты (синхронные, данные уже в памяти)
  const postsResult = calculatePostsFromCache(posts, ...);
  const lagsResult = calculateLagsFromCache(lags, ...);
  const profnastilResult = calculateProfnastilFromCache(profnastil, ...);
  
  // 3. Монтажная фурнитура (один запрос из кеша)
  const hardware = await cache.getOrSet(
    CACHE_KEYS.MOUNTING_HARDWARE(postTypeId, lagTypeId, profnastilTypeId),
    () => fetchMountingHardware([postTypeId, lagTypeId, profnastilTypeId]),
    TTL
  );
  
  // 4. Сохранение estimate
  const estimate = await prisma.fenceEstimate.create({ ... });
```

```typescript
// src/lib/cache.ts
export class CacheService {
  private redis: Redis;
  private memoryCache: Map<string, { value: any; expires: number }> = new Map();
  
  async get<T>(key: string): Promise<T | null> {
    try {
      const cached = await this.redis.get(key);
      if (cached) return JSON.parse(cached);
    } catch (error) {
      // Fallback to memory cache
      return this.getFromMemory<T>(key);
    }
    return null;
  }
  
  async getOrSet<T>(key: string, factory: () => Promise<T>, ttl: number): Promise<T> {
    const cached = await this.get<T>(key);
    if (cached !== null) return cached;
    
    const value = await factory();
    await this.set(key, value, ttl);
    return value;
  }
}

export const cache = new CacheService(redis);
```

#### TASK-BCK-011: Исправить HTTP заголовки fence-types (КРИТИЧЕСКИЙ БАГ)
**Направление**: Backend
**Приоритет**: Critical  ← повышен с Medium (главная причина 4 сек)
**Оценка**: 1 час
**Зависимости**: Нет (независимая правка, делать ПЕРВОЙ в Фазе 1)

**Описание**:
Исправить критический баг в `src/app/api/calculator/fence-types/route.ts`.
Текущий заголовок `Cache-Control: no-store` полностью отключает HTTP-кеширование,
заставляя браузер делать свежий запрос при каждом переходе между страницами калькулятора.
Это **основная причина** задержки 4 сек при загрузке типов заборов.

**Текущий баг:**
```typescript
// src/app/api/calculator/fence-types/route.ts (строки 18-23)
return NextResponse.json(result, {
  status: 200,
  headers: {
    'Cache-Control': 'no-store, no-cache, must-revalidate, proxy-revalidate', // ❌ БАГ
    'Pragma': 'no-cache',   // ❌
    'Expires': '0',         // ❌
  }
});
```

**Требуемое исправление:**
```typescript
// Вычислить ETag из данных
const etag = `"${Buffer.from(JSON.stringify(result)).length}-${Date.now()}"`;
// или стабильный hash: crypto.createHash('md5').update(JSON.stringify(result)).digest('hex')

// Поддержка 304 Not Modified
const ifNoneMatch = req.headers.get('if-none-match');
if (ifNoneMatch === etag) {
  return new NextResponse(null, { status: 304 });
}

return NextResponse.json(result, {
  status: 200,
  headers: {
    'Cache-Control': 'public, max-age=300, stale-while-revalidate=60',
    'ETag': etag,
  }
});
```

**Критерии приемки**:
- [ ] Заголовок `no-store` удалён
- [ ] `Cache-Control: public, max-age=300, stale-while-revalidate=60` установлен
- [ ] ETag вычисляется на основе стабильного хеша данных (не `Date.now()`)
- [ ] Поддержка `If-None-Match` → 304 ответ
- [ ] Браузер кеширует ответ на 5 минут (проверить в DevTools → Network)
- [ ] Unit-тесты проверяют наличие заголовков и 304 ответ
