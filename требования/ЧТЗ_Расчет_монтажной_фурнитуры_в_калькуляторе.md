## 2. Цели и задачи

### 2.1 Бизнес-цель
Обеспечить автоматический расчёт монтажной фурнитуры в калькуляторе заборов на основе привязки к номенклатуре из ЛЮБЫХ справочников (существующих и будущих).

### 2.2 Пользовательская ценность
- Автоматический расчёт фурнитуры в смете
- Поддержка различных методов расчёта (1:1, по длине, по соотношению)
- Гибкая настройка в админ-панели
- Точный расчёт метизов (саморезы, крепёж)
- **Масштабируемость** - привязка к любым справочникам без изменения кода

### 2.3 Ключевые метрики успеха
- Фурнитура корректно добавляется в смету при расчёте забора
- Все методы расчёта работают корректно
- Администратор может настроить расчёт для каждой позиции фурнитуры
- **Новые справочники автоматически доступны для привязки фурнитуры**

## 3. Анализ вариантов и лучшие практики

### 3.1 Анализ методов расчёта (Лучшие практики)

| Метод | Описание | Пример | Плюсы | Минусы |
|-------|----------|--------|-------|--------|
| **BY_QUANTITY (1:1)** | Количество фурнитуры = кол-во связанной номенклатуры | 1 заглушка на 1 столб | Простота, интуитивность | Не подходит для множественного крепежа |
| **BY_LENGTH** | Количество = Длина забора / длина единицы фурнитуры | Планка 2м на забор 10м = 5 шт | Точно для элементов с фиксированной длиной | Требует указания длины фурнитуры |
| **BY_RATIO (N:1)** | N единиц фурнитуры на 1 единицу номенклатуры | 8 саморезов на 1 лист профнастила | Гибкость для любых соотношений | Требует указания коэффициента |
| **BY_AREA** | Количество = Площадь забора / площадь единицы фурнитуры | Уплотнитель 1м² на забор 20м² × 2м = 10 шт | Точно для материалов на площадь | Требует указания площади фурнитуры |

**Важно:** Методы расчёта применяются только если в номенклатуре справочника "Монтажная фурнитура" проставлена галочка **"Использовать для расчёта в калькуляторе"**. Если галочка не проставлена — номенклатура не участвует в расчёте.

### 3.2 Анализ существующей связи с номенклатурой

**Текущая реализация:**
- Таблица `MountingHardwareRelation` содержит связи между фурнитурой и номенклатурой
- Поля: `referenceType` (LAG, POST, PROFNASTIL, PICKET, GATE, WICKET), `referenceId`
- Связь уже используется в справочнике

**Решение:** Переиспользовать существующую связь для расчёта в калькуляторе. При выборе номенклатуры (например, столбы 60х60) в калькуляторе, автоматически подтягивать связанную фурнитуру с настроенным методом расчёта.

### 3.3 Выбранная архитектура

```
┌─────────────────────────────────────────────────────────────────────────┐
│                        Калькулятор заборов                               │
├─────────────────────────────────────────────────────────────────────────┤
│  1. Выбор номенклатуры (Столбы, Лаги, Профнастил...)                    │
│  2. Расчёт количества основной номенклатуры                             │
```

### 3.4 Архитектура масштабируемых связей

**Проблема:**
Текущая реализация использует enum для `referenceType`, что требует миграции БД при добавлении новых справочников.

**Решение: Динамический реестр справочников**

```
┌─────────────────────────────────────────────────────────────────────┐
│                    Reference Registry Pattern                        │
├─────────────────────────────────────────────────────────────────────┤
│                                                                      │
│  referenceRegistry.ts (Centralized Registry)                        │
│  ├─ registerReference(type, config)                                 │
│  ├─ getReferenceConfig(type) → { name, model, service }             │
│  └─ getAllReferences() → ReferenceConfig[]                          │
│                                                                      │
│  Текущие справочники (автоматически):                               │
│  ├─ POST → PostType (Столбы)                                        │
│  ├─ LAG → LagType (Лаги)                                            │
│  ├─ PROFNASTIL → ProfnastilType (Профнастил)                        │
│  ├─ PICKET → PicketType (Евроштакетник)                             │
│  ├─ GATE → GateType (Ворота)                                        │
│  └─ WICKET → WicketType (Калитки)                                   │
│                                                                      │
│  Будущие справочники (автоматически при создании):                  │
│  └─ Любой новый справочник автоматически доступен                   │
│                                                                      │
└─────────────────────────────────────────────────────────────────────┘
```

**Ключевые принципы:**

1. **String вместо Enum:**
   ```prisma
   model MountingHardwareRelation {
     referenceType String  // Не enum! Динамический тип
     referenceId   String
     // ...
   }
   ```

2. **Реестр справочников (Registry Pattern):**
   ```typescript
   // src/lib/referenceRegistry.ts
   export interface ReferenceConfig {
     type: string;
     name: string;
     modelName: string;
     service: any;
     icon?: string;
   }
   
   class ReferenceRegistry {
     private references = new Map<string, ReferenceConfig>();
     
     register(config: ReferenceConfig) {
       this.references.set(config.type, config);
     }
     
     get(type: string): ReferenceConfig | undefined {
       return this.references.get(type);
     }
     
     getAll(): ReferenceConfig[] {
       return Array.from(this.references.values());
     }
   }
   
   export const referenceRegistry = new ReferenceRegistry();
   
   // Автоматическая регистрация при импорте
   referenceRegistry.register({
     type: 'POST',
     name: 'Столбы',
     modelName: 'PostType',
     service: postTypeService,
   });
   // ... другие справочники
   ```

3. **Динамическое получение справочников:**
   ```typescript
   // API endpoint автоматически возвращает все зарегистрированные справочники
   export async function GET() {
     const references = referenceRegistry.getAll();
     // Для каждого справочника получить позиции
     const options = await Promise.all(
       references.map(async (ref) => ({
         type: ref.type,
         name: ref.name,
         items: await ref.service.getAllActive(),
       }))
     );
     return Response.json({ references: options });
   }
   ```

4. **Валидация при создании связи:**
   ```typescript
   function validateReference(type: string, id: string) {
     const config = referenceRegistry.get(type);
     if (!config) {
       throw new Error(`Unknown reference type: ${type}`);
     }
     // Проверить, что id существует в соответствующей таблице
     return config.service.exists(id);
   }
   ```

**Преимущества:**
- ✅ Новые справочники автоматически доступны для привязки
- ✅ Не требуется миграция БД при добавлении справочника
- ✅ Централизованное управление конфигурацией
- ✅ Валидация связей на уровне приложения
- ✅ Обратная совместимость с существующими данными

**Регистрация нового справочника (пример):**
```typescript
// При создании нового справочника "Навесы"
// 1. Создаём модель CanopyType в Prisma
// 2. Создаём сервис canopyTypeService
// 3. Регистрируем в реестре:
referenceRegistry.register({
  type: 'CANOPY',
  name: 'Навесы',
  modelName: 'CanopyType',
  service: canopyTypeService,
});
// Готово! Фурнитура уже может привязываться к навесам
```

## 4. Требования к продукту

### 4.1 Функциональные требования

#### 4.1.1 Добавление полей в справочник "Монтажная фурнитура"

**User Story 1: Настройка расчёта фурнитуры в админ-панели**

*Как администратор, я хочу указать для каждой позиции фурнитуры - участвует ли она в расчёте калькулятора и каким методом рассчитывается.*

**Acceptance Criteria:**
- [ ] Добавлена галочка "Используется при расчёте в калькуляторе" (useInCalculator)
- [ ] Если галочка снята — номенклатура не участвует в расчёте (просто хранится в справочнике)
- [ ] Если галочка установлена — обязательно выбрать метод расчёта
- [ ] Добавлено поле "Метод расчёта" (calculationMethod) с выпадающим списком:
  - По количеству (1:1) — BY_QUANTITY
  - По длине забора — BY_LENGTH
  - По площади забора (м²) — BY_AREA
  - По соотношению — BY_RATIO
- [ ] При выборе BY_LENGTH появляется поле "Длина единицы (м)" (calculationValue)
- [ ] При выборе BY_AREA появляется поле "Площадь единицы (м²)" (calculationValue)
- [ ] При выборе BY_RATIO появляется поле "Коэффициент" (calculationValue)
  - Если > 1: N единиц фурнитуры на 1 единицу номенклатуры (8 саморезов на лист)
  - Если < 1: 1 единица фурнитуры на N единиц номенклатуры (1/4 мешка на столб)
- [ ] Поля отображаются в таблице справочника (колонка "В калькуляторе")

**Примечание:** Методы расчёта применяются только если `useInCalculator = true`. Если галочка снята — номенклатура существует в справочнике, но не участвует в автоматическом расчёте калькулятора.

#### 4.1.2 Расчёт фурнитуры в калькуляторе

**User Story 2: Автоматический расчёт фурнитуры при расчёте забора**

*Как система, я хочу автоматически рассчитывать количество фурнитуры на основе выбранной номенклатуры и настроенного метода расчёта.*

**Acceptance Criteria:**
- [ ] При расчёте забора калькулятор получает связанную фурнитуру (useInCalculator = true)
- [ ] Для каждой позиции фурнитуры применяется соответствующий метод расчёта:
  - **BY_QUANTITY**: количество фурнитуры = количество связанной номенклатуры
    - Пример: 6 столбов → 6 заглушек
  - **BY_LENGTH**: количество = roundUp(длина_забора / длина_единицы_фурнитуры)
    - Пример: забор 10м, планка 2м → roundUp(10/2) = 5 планок
  - **BY_AREA**: количество = roundUp(площадь_забора / площадь_единицы_фурнитуры)
    - Пример: забор 10м×2м = 20м², планка на 4м² → roundUp(20/4) = 5 планок
  - **BY_RATIO**: количество = roundUp(кол-во_номенклатуры * коэффициент)
    - Пример (коэф > 1): 8 листов профнастила × 8 саморезов = 64 самореза
    - Пример (коэф < 1): 6 столбов × 0.25 мешка = roundUp(1.5) = 2 мешка
- [ ] Рассчитанная фурнитура добавляется в общую смету (materials)
- [ ] Результат включает: название, количество, единица измерения, цена, сумма

**Примечание:** Реализация логики расчёта в калькуляторе будет выполнена отдельной задачей. Данный ЧТЗ описывает только параметры и настройку методов.

*Как администратор, я хочу привязывать монтажную фурнитуру к любым справочникам системы, включая те, которые будут созданы в будущем.*

**Acceptance Criteria:**
