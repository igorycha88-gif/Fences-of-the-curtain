## 1. Контекст инцидента

**Триггер:** пользователь не смог войти в админку на проде (zabor-i-naves.ru) 03.11.2026 ~09:20 МСК.

**Диагностика (по логам `fences-app` на VPS, Redis, БД):**

- Backend авторизации исправен: `authorize()` → JWT → `/api/auth/session` → `/api/auth/me` — все этапы успешны, роль ADMIN. Пользователь 3 раза входил и работал в админке (08:59–09:19 МСК).
- В 09:19 МСК рейт-лимит (`rate_limit:auth:79.174.33.202:admin@fences.ru`) достиг 5 попыток → IP+email заблокированы на 15 мин. Сообщение на фронте — «Неверный email или пароль».
- В 09:20 МСК пользователь попробовал другой email — такого пользователя нет в БД → «User not found or inactive».
- Таблица `RateLimitConfig` пуста → действует дефолт: 5 попыток / 15 мин (`src/lib/rate-limit.ts:30`).

## 2. Корневые причины

### BUG-001: Успешный вход не сбрасывает счётчик рейт-лимита

`resetRateLimit(ip, email)` реализован (`src/lib/rate-limit.ts:120`), но **нигде не вызывается**. `checkRateLimit()` инкрементирует счётчик на КАЖДОЙ попытке, включая успешные. Итог: 5 входов (даже успешных) за 15 минут → блокировка с правильным паролем.

### BUG-002: Ложное сообщение при блокировке

При превышении лимита `authorize()` возвращает `null` → NextAuth отдаёт `CredentialsSignin` → фронт показывает «Неверный email или пароль» (`src/app/admin/login/page.tsx:30`). Пользователь не знает о блокировке и продолжает попытки (в инциденте — 3 попытки за 11 секунд), продлевая фрустрацию.

## 3. Задачи

### TASK-BCK-001: Сброс счётчика при успешной авторизации

Файл: `src/lib/auth.ts`

- После успешной проверки пароля (строка ~115, перед `return`) вызвать `await resetRateLimit(ip, credentials.email)` в try/catch (ошибка сброса не должна блокировать вход, но логируется через структурированный logger).
- Заменить оставшиеся `console.log/console.error` в `src/lib/auth.ts` на структурированный logger (`src/lib/logger.ts`) с контекстом `{ module: 'auth', operation, ... }` — паритет с Правилом 8. В логах НЕ логировать пароль и полный email (маскировать, см. `maskEmail`).

### TASK-BCK-002: Фиксированное окно вместо скользящего

Файл: `src/lib/rate-limit.ts`, функция `checkRateLimit`

- Сейчас `multi.expire(key, ...)` обновляется на каждой попытке → окно «скользит» и каждая попытка продлевает блокировку. Привести к поведению `applyRateLimitByEndpoint` (строки 194–196): TTL устанавливается только при первом инкременте (`attempts === 1`). Легитимный пользователь получает гарантированный момент разблокировки.

### TASK-BCK-003: Различимый статус блокировки для фронта

Файлы: `src/app/api/auth/login-status/route.ts` (новый), при необходимости `src/lib/rate-limit.ts`

- Новый GET-эндпоинт `/api/auth/login-status?email=<email>`:
  - Ответ: `{ blocked: boolean, resetAt: string | null }` (использовать существующую `getRateLimitStatus`).
  - Сам эндпоинт защищён IP-рейт-лимитом через `applyRateLimitByEndpoint` (тип `auth`), чтобы не стать вектором перебора.
  - Не раскрывает существование email (отвечает одинакового для любого email).
  - Логирование request/response через logger (Правило 8), `export const dynamic = 'force-dynamic'`.
- Альтернатива реализации допускается, если Разработчик предложит более чистый механизм передачи причины отказа через NextAuth v4 (например, прокидывание кода ошибки) — критерием является выполнение критериев приёмки K-3.

### TASK-FRT-001: Честное сообщение о блокировке на странице логина

Файл: `src/app/admin/login/page.tsx`

- При ошибке входа (`result.error`) запросить `/api/auth/login-status`; при `blocked: true` показать: «Слишком много попыток входа. Попробуйте через N минут» (N — из `resetAt`, округление вверх до минут) вместо «Неверный email или пароль».
- Сообщение о блокировке не должно позволять повторную отправку формы до разблокировки (кнопка заблокирована или показан таймер — на усмотрение Разработчика, минимум: честный текст).
- Существующее поведение при обычной ошибке пароля не меняется.

## 4. Критерии приёмки

- **K-1:** После успешного входа счётчик `rate_limit:auth:<ip>:<email>` в Redis удалён (проверяется тестом с mock-редисом).
- **K-2:** TTL ключа не продлевается при повторных неудачных попытках: 2-я…5-я попытка не сбрасывают TTL первой (тест).
- **K-3:** При заблокированном аккаунте/IP страница логина показывает сообщение о блокировке с оставшимся временем, а не «Неверный email или пароль» (тест компонента).
- **K-4:** `/api/auth/login-status` отвечает 200 `{blocked:false}` для незаблокированного, `{blocked:true, resetAt}` для заблокированного; при превышении собственного лимита — 429; не раскрывает существование email (одинаковая структура ответа).
- **K-5:** Все изменённые/новые файлы используют структурированный logger (нет голых console.*), в логах нет паролей и полных email.
- **K-6:** `npm test && npm run lint && npx tsc --noEmit` — зелёные; покрытие новых/изменённых файлов ≥ 60%.
- **K-7:** Регресс: обычный вход с верным/неверным паролем работает как раньше (happy path тесты логина не сломаны).
