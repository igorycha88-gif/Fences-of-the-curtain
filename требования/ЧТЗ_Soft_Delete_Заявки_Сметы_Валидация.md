# ЧТЗ: Soft Delete для Заявок и Смет + Исправление валидации номенклатуры

**Дата:** 2026-04-09  
**Автор:** Аналитик (AI)  
**Приоритет:** Высокий  

---

## 1. Бизнес-задачи

### Задача A: Удаление Заявок (soft delete)
Администратор должен иметь возможность удалить заявку из справочника «Заявки». Удалённая заявка не отображается, но остаётся в БД (становится неактивной).

### Задача B: Удаление Смет (soft delete)
Администратор должен иметь возможность удалить смету из справочника «Расчеты». Удалённая смета не отображается, но остаётся в БД (становится неактивной).

### Задача C: Исправление бага валидации номенклатуры
При редактировании существующей номенклатуры в справочнике (столбы и др.) срабатывает некорректная валидация «уже существует», хотя редактируется та же самая запись.

---

## 2. Критерии приёмки

### AC-A: Soft Delete Заявок
- **AC-A1:** В таблице списка заявок (`/admin/orders`) в конце каждой строки отображается красная иконка корзины (Trash2), видимая ТОЛЬКО администратору (role=ADMIN)
- **AC-A2:** На странице деталей заявки (`/admin/orders/[id]`) отображается красная кнопка «Удалить», видимая ТОЛЬКО администратору
- **AC-A3:** При нажатии на удаление появляется модальное окно подтверждения с текстом «Удалить заявку?» и кнопками «Отмена» / «Удалить»
- **AC-A4:** После подтверждения заявка помечается в БД как `active: false` (soft delete), данные НЕ удаляются физически
- **AC-A5:** Неактивные заявки НЕ отображаются в списке заявок
- **AC-A6:** Менеджер (MANAGER) и контент-менеджер (CONTENT_MANAGER) НЕ видят кнопку удаления
- **AC-A7:** После удаления пользователь перенаправляется на список заявок с уведомлением об успешном удалении
- **AC-A8:** Audit Log регистрирует факт удаления (soft delete)

### AC-B: Soft Delete Смет
- **AC-B1:** В таблице списка расчётов (`/admin/estimates`) в конце каждой строки отображается красная иконка корзины, видимая ТОЛЬКО администратору
- **AC-B2:** В модальном окне детальной информации сметы отображается красная кнопка «Удалить», видимая ТОЛЬКО администратору
- **AC-B3:** На отдельной странице сметы (`/admin/estimates/[id]`) отображается красная кнопка «Удалить», видимая ТОЛЬКО администратору
- **AC-B4:** При нажатии появляется модальное окно подтверждения
- **AC-B5:** После подтверждения смета помечается как `active: false`, данные НЕ удаляются физически
- **AC-B6:** Неактивные сметы НЕ отображаются в списке расчётов
- **AC-B7:** Менеджер и контент-менеджер НЕ видят кнопку удаления
- **AC-B8:** Audit Log регистрирует факт удаления

### AC-C: Исправление валидации номенклатуры
- **AC-C1:** При редактировании существующей номенклатуры без изменения уникальных полей (изменение цены, описания и т.д.) валидация НЕ срабатывает — сохранение проходит успешно
- **AC-C2:** При изменении уникальных полей на значения, которые уже есть у ДРУГОЙ записи — валидация корректно срабатывает
- **AC-C3:** Исправление применяется ко ВСЕМ затронутым справочникам: PostType, LagType, ProfnastilType, PicketType, Panel3D

## 3. Технический анализ

### 3.1. Текущее состояние

| Компонент | Order | FenceEstimate | MultiFenceEstimate |
|-----------|-------|---------------|---------------------|
| Поле `active` в Prisma | НЕТ | НЕТ | НЕТ |
| DELETE API endpoint | Есть (hard delete) | НЕТ | НЕТ |
| Кнопка удаления в UI | НЕТ | НЕТ | НЕТ |

### 3.2. Корневая причина бага валидации

**Затронутые сервисы:** `profnastilTypeService`, `picketTypeService`, `panel3dService`, `postTypeService`

**Суть бага:** При обновлении записи guard-условие проверки дубликатов ВСЕГДА `true`, т.к. форма отправляет ВСЕ поля (включая `name`). Из-за этого проверка запускается на КАЖДОЕ редактирование, даже если уникальные поля не изменены. Если в БД есть другая запись с совпадающими уникальными полями (например, неактивная), сохранение блокируется.

**Детали по сервисам:**
- `profnastilTypeService.ts:194` — условие `data.name || data.metalThickness || data.coating || data.color !== undefined` всегда true
- `picketTypeService.ts:180` — аналогично
- `panel3dService.ts:209` — аналогично + отсутствует проверка rodDiameter, cellWidth, cellHeight
- `postTypeService.ts:244-265` — отсутствует `length` в проверке при обновлении

**Решение:** Изменить guard-условие — сравнивать новые значения со старыми и запускать проверку ТОЛЬКО если уникальные поля действительно изменились.

## 6. Риски и ограничения

1. **Миграция БД:** Все существующие Order и FenceEstimate получат `active: true` по умолчанию — это корректно
2. **Связанные данные:** При soft delete заявки связанные сметы остаются активными (и наоборот) — это допустимо, т.к. они нужны для аналитики
3. **Публичный API:** Калькулятор создаёт FenceEstimate — эти записи не должны затрагиваться фильтром `active`, т.к. это сделано в админ-панели
4. **Обратная совместимость:** Существующие ссылки на неактивные заявки/сметы вернут 404 — это ожидаемое поведение
