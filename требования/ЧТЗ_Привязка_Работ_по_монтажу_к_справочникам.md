## 3. Требования к продукту

### 3.1 Функциональные требования

#### 3.1.1 Существующая модель Work

Текущая структура модели Work в БД:
```prisma
model Work {
  id              String         @id @default(cuid())
  name            String
  description     String?
  category        String
  unit            String
  price           Float
  useInCalculator Boolean        @default(false)
  sortOrder       Int            @default(0)
  active          Boolean        @default(true)
  createdAt       DateTime       @default(now())
  updatedAt       DateTime       @updatedAt
  relations       WorkRelation[]
}
```

Текущая модель WorkRelation:
```prisma
model WorkRelation {
  id        String   @id @default(cuid())
  workId    String
  fenceType String
  createdAt DateTime @default(now())
  work      Work     @relation(fields: [workId], references: [id], onDelete: Cascade)

  @@unique([workId, fenceType])
}
```

**Текущая функциональность:**
- Work привязывается только к типу забора (fenceType)
- Поле useInCalculator для включения в калькулятор
- Связь: Work → WorkRelation → FenceType

---

#### 3.1.2 Расширение модели WorkRelation

**User Story 1: Привязка работ к номенклатуре ворот и калиток**

*Как администратор, я хочу привязать работы по монтажу к конкретной номенклатуре из справочников Ворота или Калитки.*

**Acceptance Criteria:**
- [ ] WorkRelation расширяется для поддержки привязки к конкретной номенклатуре
- [ ] Добав поле `referenceType` для указания типа справочника (существующий fenceType + новые GATE, WICKET)
- [ ] Добавлено поле `referenceId` для указания конкретной позиции справочника
- [ ] Сохранена обратная совместимость с существующими связями по fenceType

**Новая схема данных:**
```prisma
model WorkRelation {
  id           String   @id @default(cuid())
  workId       String
  fenceType    String?  // Для обратной совместимости - может быть null
  referenceType String? // Новый: GATE, WICKET, и др.
  referenceId  String?  // Новый: ID конкретной номенклатуры
  createdAt    DateTime @default(now())

  work         Work     @relation(fields: [workId], references: [id], onDelete: Cascade)

  @@unique([workId, fenceType, referenceType, referenceId])
  @@index([fenceType])
  @@index([referenceType])
  @@index([referenceId])
}
```

**Логика работы:**
- Если `fenceType` заполнен → работа привязана к типу забора (существующая логика)
- Если `referenceType` + `referenceId` заполнен → работа привязана к конкретной номенклатуре
- Оба варианта могут использоваться одновременно

#### 3.1.6 Расчёт в калькуляторе для Work с привязкой к номенклатуре

**User Story 5: Автоматический расчёт работ при выборе номенклатуры**

*Как система, я хочу автоматически добавлять работу в смету если выбрана связанная номенклатура.*

**Acceptance Criteria:**
- [ ] При расчёте калькулятора проверяется наличие Work с useInCalculator = true
- [ ] Для каждого Work проверяются связи:
  - Если есть привязка к referenceType + referenceId → проверяется, выбрана ли эта номенклатура
  - Если есть привязка к fenceType → работа добавляется для всех заборов этого типа
- [ ] Работа добавляется в смету если:
  - useInCalculator = true
  - И (есть привязка к referenceId который выбран) ИЛИ (есть привязка к fenceType текущего забора)
- [ ] Рассчитанная работа добавляется в общую стоимость

**Flow расчёта:**
```
1. Пользователь выбирает: Забор + Номенклатура (Ворота, Калитки)
2. Калькулятор проверяет Work с useInCalculator = true
3. Для каждого Work проверяет связи:
   - Проверяет referenceId: совпадает с выбранной номенклатурой?
   - Проверяет fenceType: совпадает с типом забора?
4. Если совпадение найдено → добавляет работу в смету
```
