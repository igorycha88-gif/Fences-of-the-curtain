## 2. Цели и задачи

### 2.1 Бизнес-цель
Исправить ошибки в алгоритме расчета стоимости лаг для получения корректных смет заборов.

### 2.2 Пользовательская ценность
Клиенты получают точные расчеты стоимости материалов, исключающие ошибки при заказе.

### 2.3 Ключевые метрики
- Устранение расхождений в расчетах смет
- Корректное отображение стоимости материалов в калькуляторе

## 3. Анализ текущей реализации

### 3.1 Текущие формулы

**Файл**: `src/services/calculator/lagCalculator.ts`

```
Количество лаг (строки 60-61):
  lagsPerRow = roundUp(Длина_забора_мм / Длина_лаги_мм) + 2
  totalLags = lagsPerRow × Количество_рядов

Стоимость (строки 63-64):
  pricePerUnit = basePricePerMeter × (Длина_лаги_мм / 1000)
  totalPrice = totalLags × pricePerUnit
```

### 3.2 Проблемы

| # | Проблема | Описание |
|---|----------|----------|
| 1 | **Неверная формула количества** | +2 лаги добавляются к каждому ряду, а не к общему количеству |
| 2 | **Неверное именование поля** | Поле `basePricePerMeter` используется как розничная цена, но название не отражает суть |

### 3.3 Пример текущего расчета (200м забор, 2 ряда, лага 3м)

```
lagsPerRow = roundUp(200000 / 3000) + 2 = 67 + 2 = 69
totalLags = 69 × 2 = 138 шт  ← НЕВЕРНО
pricePerUnit = 520 × 3 = 1560 руб
totalPrice = 138 × 1560 = 215 280 руб
```

**Ожидаемый результат**:
```
totalLags = 67 × 2 + 2 = 136 шт  ← ВЕРНО
totalPrice = 136 × 1560 = 212 160 руб
```

## 4. Функциональные требования

### FR-1: Корректировка формулы количества лаг

**User Story**:
> Как система расчета сметы, я хочу корректно рассчитывать количество лаг, чтобы клиент получал точную смету.

**Текущая формула**:
```
lagsPerRow = roundUp(Длина_забора_мм / Длина_лаги_мм) + 2
totalLags = lagsPerRow × Количество_рядов
```

**Новая формула**:
```
baseLagsPerRow = roundUp(Длина_забора_мм / Длина_лаги_мм)
totalLags = baseLagsPerRow × Количество_рядов + 2
```

**Обоснование**: 2 дополнительные лаги добавляются на весь забор для компенсации стыков и обрезков, а не на каждый ряд отдельно.

**Acceptance Criteria**:

```gherkin
Scenario: Расчет количества лаг для забора 200м
  Given длина забора 200 метров
  And длина лаги 3 метра (3000 мм)
  And количество рядов лаг 2
  When система рассчитывает количество лаг
  Then baseLagsPerRow = roundUp(200000 / 3000) = 67
  And totalLags = 67 × 2 + 2 = 136 шт

Scenario: Расчет количества лаг для забора 100м с 3 рядами
  Given длина забора 100 метров
  And длина лаги 3 метра (3000 мм)
  And количество рядов лаг 3
  When система рассчитывает количество лаг
  Then baseLagsPerRow = roundUp(100000 / 3000) = 34
  And totalLags = 34 × 3 + 2 = 104 шт
```

**Матрица тестовых значений**:

| Длина забора | Длина лаги | Ряды | Было (шт) | Стало (шт) | Разница |
|--------------|------------|------|-----------|------------|---------|
| 200м | 3м | 2 | 138 | **136** | -2 |
| 100м | 3м | 3 | 102 | **102** | 0 |
| 50м | 3м | 2 | 36 | **36** | 0 |
| 150м | 3м | 2 | 104 | **102** | -2 |
| 300м | 3м | 3 | 204 | **302** | +98 |

### FR-2: Переименование поля цены

**User Story**:
> Как администратор системы, я хочу видеть понятные названия полей в справочнике лаг, чтобы избежать путаницы между закупочной и розничной ценой.

**Изменение**:
- Переименовать поле `basePricePerMeter` → `retailPricePerMeter`
- Поле `purchasePricePerMeter` уже существует и остается без изменений

**Обоснование**: В схеме уже есть `purchasePricePerMeter` (закупочная цена). Для консистентности розничная цена должна называться `retailPricePerMeter`.

**Структура полей цены в LagType после изменений**:

| Поле | Тип | Описание |
|------|-----|----------|
| `retailPricePerMeter` | Float | Розничная цена за метр (для расчета смет) |
| `purchasePricePerMeter` | Float? | Закупочная цена за метр (для аналитики) |
