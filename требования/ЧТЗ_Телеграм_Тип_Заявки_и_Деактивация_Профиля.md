# ЧТЗ: Корректный тип заявки в Telegram-уведомлении + деактивация профиля «Полукруглый (С-образный)»

- **Дата:** 2026-11-03
- **Маршрут:** 1 (Стандартная: Аналитик → Разработчик → Тестировщик → DevOps)
- **Тип:** Малая задача (упрощённое ЧТЗ), баг-фикс + изменение справочных данных
- **Автор:** Аналитик (конвейер)
- **Статус:** Утверждено пользователем

## 1. Проблема

1. **Баг уведомления.** В Telegram-уведомлении по новой заявке тип выводится тернарником
   `serviceType === 'fence' ? 'Забор' : 'Навес'` (`src/services/telegram/bot.ts:114`).
   Все заявки с `serviceType` ≠ `'fence'` (включая `INDIVIDUAL_CALCULATION`, `gates`, `garage`)
   показываются как «Навес». Пример: заявка `cmw09wjda0004dclsgnrr6c3z` (Елена, забор из
   евроштакетника, индивидуальный расчёт) ушла в Telegram с типом «Навес».

2. **Пустой справочник.** Профиль пикета «Полукруглый (С-образный)»
   (`PicketProfileType.id = e8689d4e-d3db-4029-a48e-f8b3eb3b1b99`) активен, но не имеет ни одной
   записи `PicketType` (нет на складе). Клиенты выбирают его в калькуляторе → смета не строится →
   падают в «индивидуальный расчёт». Требуется деактивация до появления товара.

## 2. Решение

### 2.1. Код (TASK-BCK-1, TASK-BCK-2)

**Файл:** `src/services/telegram/bot.ts`

Ввести функцию `getOrderTypeLabel(order)`:

| `serviceType` | `parameters` | Метка в уведомлении |
|---|---|---|
| `fence` | — | `Забор` |
| `canopy` | — | `Навес` |
| `gates` | — | `Ворота` |
| `garage` | — | `Гараж` |
| `INDIVIDUAL_CALCULATION` | `fenceTypeId` или `fenceTypeName` | `Индивидуальный расчёт (забор)` + `, ${fenceTypeName}` при наличии |
| `INDIVIDUAL_CALCULATION` | `canopyType` или `purpose` | `Индивидуальный расчёт (навес)` |
| `INDIVIDUAL_CALCULATION` | `serviceType === 'gates'` | `Индивидуальный расчёт (ворота)` |
| `INDIVIDUAL_CALCULATION` | `serviceType === 'garage'` | `Индивидуальный расчёт (гараж)` |
| `INDIVIDUAL_CALCULATION` | пусто/не распознано | `Индивидуальный расчёт` |
| иное/отсутствует | — | значение `serviceType` как есть |

Дискриминаторы подтверждены схемой `src/lib/validators/order.ts:28-87`
(`fenceParametersSchema`, `canopyParametersSchema`, `garageParametersSchema`, `gateParametersSchema`
мержатся в единый `parameters` при `createIndividualOrder`, `src/app/api/orders/route.ts:392-414`).

Заменить в `sendOrderNotification` тернарник на вызов `getOrderTypeLabel(order)`.

**Логирование:** существующее в `sendTelegramMessage` достаточно (функция только форматирует текст,
сетевых операций не добавляется).

**Тесты (TASK-BCK-2):** расширить `__tests__/services/telegram-bot.test.ts`:
- happy path для каждой строки таблицы выше (10 кейсов);
- регресс: `serviceType: 'fence'` → «Забор» (существующий тест остаётся зелёным);
- escaping не сломан (имя с `<b>` как раньше).

### 2.2. Данные на проде (TASK-INF-1, выполняет DevOps)

```sql
UPDATE "PicketProfileType"
SET active = false, "updatedAt" = now()
WHERE id = 'e8689d4e-d3db-4029-a48e-f8b3eb3b1b99' AND active = true;
-- ожидается UPDATE 1
```

Инвалидация кеша (Redis, TTL 300 с): `DEL calculator:picket:profile-types:active`.

Деплой кода на прод — НЕ входит в это ЧТЗ (отдельный триггер «деплой на прод»).

## 3. Критерии приёмки

1. `sendOrderNotification` для всех `serviceType` из таблицы §2.1 выводит корректный тип.
2. Для заявки `cmw09wjda...` (и аналогичных индивидуальных заборов) метка —
   `Индивидуальный расчёт (забор), Евроштакетник`.
3. Ни одно сочетание не выводит неверный тип «Навес» (кроме реального навеса).
4. Новые unit-тесты покрывают все строки таблицы §2.1 + регресс + escaping; `npm test`,
   `npm run lint`, `npx tsc --noEmit` — зелёные.
5. На проде профиль `e8689d4e-...` `active = false`; в API
   `GET /api/calculator/picket-profile-types` он отсутствует; кеш инвалидирован.
6. Локально: полная пересборка dev-контейнеров, healthcheck healthy, `/api/health` — 200.

- Минимальные: правка затрагивает только текст Telegram-сообщения.
