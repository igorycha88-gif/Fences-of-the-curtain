## 2. Цели и задачи

### 2.1 Бизнес-цель
Обеспечить возможность учета себестоимости материалов (лаг и столбов) для расчета маржинальности и прибыльности заказов. Позволить администраторам видеть реальную стоимость материалов и принимать решения о ценообразовании на основе данных о закупке.

### 2.2 Пользовательская ценность
Администраторы получают возможность:
- Указывать закупочные цены для разных длин материалов
- Видеть маржинальность по каждому типу материала
- Анализировать рентабельность различных конфигураций заборов
- Принимать обоснованные решения о ценообразовании

### 2.3 Ключевые метрики успеха
- 100% новых материалов создаются с указанием цены закупки (опционально)
- Корректный расчет маржи в отчетах
- Доступ к данным только у ADMIN роли
- Полное логирование изменений цен закупки

## 3. Требования к продукту

### 3.1 Функциональные требования

#### 3.1.1 Управление ценами закупки для Лаг

**User Story 1: Добавление цены закупки при создании лаги**
*Как администратор, я хочу указать цену закупки для каждой длины лаги, чтобы видеть маржинальность.*

**Acceptance Criteria:**
- Форма создания лаги содержит секцию "Цены закупки" (видима только ADMIN)
- Для каждой доступной длины из availableLengths можно указать цену закупки
- Формат: `{ length: 2.5, purchasePrice: 120 }`
- Поле опциональное - можно создать лагу без указания цены закупки
- Валидация:
  - purchasePrice ≥ 0
  - purchasePrice может быть null (не указана)
  - Если указана, warning если purchasePrice ≥ basePricePerMeter (наценка ≤ 0)
- После сохранения:
  - Данные сохраняются в поле purchasePrices (Json)
  - Изменения логируются в ReferenceChangeLog
- UI:
  - Таблица с колонками: Длина, Цена продажи, Цена закупки, Маржа
  - Автоматический расчет маржи в реальном времени
  - Цветовая индикация: зеленый (маржа > 30%), желтый (10-30%), красный (< 10%)

**User Story 2: Редактирование цены закупки лаги**
*Как администратор, я хочу изменить цену закупки существующей лаги.*

**Acceptance Criteria:**
- Форма редактирования лаги показывает текущие цены закупки (только ADMIN)
- Можно изменить purchasePrice для любой длины
- Можно добавить purchasePrice для длины, где она не была указана
- Можно удалить purchasePrice (очистить поле)
- Валидация аналогично User Story 1
- После сохранения:
  - Изменения применяются
  - Запись в ReferenceChangeLog:
    - entityType: "LagType"
    - entityId: ID лаги
    - fieldName: "purchasePrices"
    - oldValue: предыдущее значение JSON
    - newValue: новое значение JSON
    - changedBy: ID пользователя
    - changedAt: timestamp

**User Story 3: Просмотр цены закупки в списке лаг**
*Как администратор, я хочу видеть цену закупки в таблице лаг для быстрой оценки маржи.*

**Acceptance Criteria:**
- Таблица лаг содержит колонку "Цена закупки" (видима только ADMIN)
- Формат отображения: "120 ₽/м.п." или "Не указана"
- Сортировка по цене закупки
- Фильтрация: "С ценой закупки" / "Без цены закупки"
- Tooltip при наведении показывает детализацию по длинам

**User Story 8: Ограничение доступа к ценам закупки**
*Как система, я хочу скрыть цены закупки от пользователей с ролью MANAGER и CONTENT_MANAGER.*

**Acceptance Criteria:**
- Роль ADMIN: видит и редактирует цены закупки

  - Секция "Цены закупки" скрыта для не-ADMIN

#### 3.1.5 Отчетность и аналитика

**User Story 9: Расчет маржинальности материала**
*Как администратор, я хочу видеть маржинальность каждого материала в реальном времени.*

**Acceptance Criteria:**
- Автоматический расчет маржи при вводе цен:
  ```
  Маржа (%) = (Цена продажи - Цена закупки) / Цена продажи * 100%
  ```
- Отображение маржи в форме создания/редактирования:
  - Зеленый цвет: маржа ≥ 30%
  - Желтый цвет: маржа 10-30%
  - Красный цвет: маржа < 10%
  - Серый цвет: цена закупки не указана
- Tooltip показывает:
  - Абсолютная маржа в рублях: "Маржа: 30 ₽/м.п."
  - Процентная маржа: "Маржа: 20%"

**User Story 10: Экспорт данных для финансовой отчетности**
*Как администратор, я хочу экспортировать данные о ценах закупки для финансового анализа.*

**Acceptance Criteria:**
- Кнопка "Экспорт в CSV" на странице списка лаг/столбов (только ADMIN)
- Формат CSV:
  ```
  Название,Длина,Цена продажи,Цена закупки,Маржа (%),Маржа (₽)
  Профиль 40x20x2.0,2.5,150,120,20%,30
  Профиль 40x20x2.0,3.0,180,145,19.4%,35
  ```
- Фильтрация перед экспортом:
  - Только активные
  - Только с ценой закупки
  - По диапазону маржи

## 10. Риски и зависимости

### 10.1 Технические риски

**Risk 1: Breaking Change при удалении priceWithConcrete**

**Category:** Technical  
**Probability:** Medium  
**Impact:** Medium

**Description:**
Удаление поля priceWithConcrete может повлиять на существующий код или интеграции, которые используют это поле.

**Potential Impact:**
1. Ошибки в frontend компонентах, которые отображают priceWithConcrete
2. Ошибки в API клиентах, которые ожидают это поле
3. Потеря данных при миграции (исторические данные)

**Mitigation Strategies:**
1. **Prevent:** Провести полный поиск использования priceWithConcrete в кодовой базе
2. **Mitigate:** Создать тесты, проверяющие отсутствие поля в API ответах
3. **Accept:** Уведомить пользователей API о breaking change заранее

**Owner:** Backend Developer  
**Review Date:** Перед релизом

---

**Risk 2: Производительность при расчете маржи для больших списков**

**Category:** Technical  
**Probability:** Low  
**Impact:** Low

**Description:**
Расчет маржи на клиенте для большого количества записей может замедлить отображение списков.

**Potential Impact:**
1. Долгая загрузка страницы списка лаг/столбов (>2 сек)
2. Плохой UX при фильтрации и сортировке

**Mitigation Strategies:**
1. **Prevent:** Оптимизировать расчет маржи (кеширование на клиенте)
2. **Mitigate:** Добавить пагинацию для больших списков
3. **Accept:** Ограничить количество записей на странице (50 записей)

**Owner:** Frontend Developer  
**Review Date:** После реализации

---

**Risk 3: Некорректные данные в purchasePrices**

**Category:** Technical  
**Probability:** Medium  
**Impact:** Low

**Description:**
Пользователи могут вводить некорректные данные (отрицательные цены, цены > цены продажи), что приведет к некорректным расчетам маржи.

**Potential Impact:**
1. Отрицательная или >100% маржа
2. Некорректные отчеты
3. Путаница у пользователей

**Mitigation Strategies:**
1. **Prevent:** Валидация на клиенте и сервере (warning для некорректных данных)
2. **Mitigate:** Цветовая индикация проблемных значений
3. **Accept:** Разрешить сохранение warning данных (гибкость)

**Owner:** Backend Developer  
**Review Date:** После реализации

---

### 10.2 Бизнес риски

**Risk 4: Сопротивление пользователей введению цен закупки**

**Category:** Business  
**Probability:** Low  
**Impact:** Medium

**Description:**
Администраторы могут не захотеть вводить цены закупки из-за дополнительной работы или нежелания раскрывать информацию о марже.

**Potential Impact:**
1. Низкое заполнение поля purchasePrices
2. Некорректные данные о марже
3. Функционал не используется

**Mitigation Strategies:**
1. **Prevent:** Объяснить ценность функционала (отчетность, аналитика)
2. **Mitigate:** Сделать поле опциональным
3. **Transfer:** Провести обучение пользователей

**Owner:** Product Manager  
**Review Date:** Через 2 недели после релиза

---
