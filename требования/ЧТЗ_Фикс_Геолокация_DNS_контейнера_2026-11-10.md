# ЧТЗ: Фикс геолокации — DNS-резолвер контейнера (город пользователя снова не определяется)

**Дата:** 2026-11-10
**Маршрут:** Аналитик → Разработчик → Тестировщик → DevOps (единый деплой: код + DNS-фикс + бэкфилл)
**Тип:** Баг-фикс (инфраструктура + код)
**Решение пользователя (10.11.2026):** срочный hotfix-рестарт контейнера НЕ выполняется; TASK-INF-1 применяется в рамках планового полного деплоя (Blue-Green) вместе с TASK-BCK-1. Порядок: код → тесты → деплой (включая dns: 77.88.8.8/77.88.8.1) → бэкфилл TASK-BCK-2.

## Проблема

С **04.11.2026** на проде снова не определяется город пользователей:
- в админке у новых расчётов город пустой (последняя запись с городом — 03.11);
- в телеграм-уведомлениях нет строки «📍 Локация»;
- в «Гео посетителей» — «Не определён».

Это 2-й инцидент за месяц (первый: 23.10–02.11, деградация DNS хостера — см. `ЧТЗ_Фикс_Геолокация_Город_Пользователя.md`).

## Диагностика (проведена на проде 10.11.2026)

1. **Логи:** за 48ч — 170 ошибок `IP lookup provider fetch failed ... durationMs:6000`, **0 успешных**. Оба провайдера (ip-api, ipwho) таймаутят ровно на 6с — соединение не устанавливается.
2. **С хоста VPS:** DNS быстрый (3–60 мс), `curl http://ip-api.com/json/...` — 200 за 0.17 с, `ipwho.is` — 200 за 0.27 с. т.е. сеть и провайдеры внешне доступны.
3. **Из контейнера (Node):** `dns.resolve4('ip-api.com')` @8.8.8.8 и @1.1.1.1 — **ETIMEOUT (22–53 с)**; @77.88.8.8 и @77.88.8.1 — **OK за 19–27 мс**.
4. **Первопричина:**
   - контейнер `fences-app` (network_mode: host) имеет собственный `/etc/resolv.conf` с `nameserver 8.8.8.8, 8.8.4.4` — Docker подставил свои дефолтные Google DNS, потому что хостовый resolv.conf указывает на локальный stub `127.0.0.53` (Docker игнорирует localhost-неймсерверы);
   - с ~04.11 сеть хостера перестала пропускать UDP-DNS к Google (8.8.8.8/8.8.4.4) и Cloudflare (1.1.1.1) — ETIMEOUT из контейнера;
   - на хосте systemd-resolved пережил это автоматически (переключился на `77.88.8.8`), поэтому диагностика с хоста «зелёная», а Node в контейнере — нет.
5. **БД (FenceEstimate, город по дням):** 31.10–03.11 — заполнен у 100% записей; с 04.11 — у 0% (18 записей без города: 04.11 — 3, 06.11 — 1, 09.11 — 12, 10.11 — 2).

**Вывод: код (ретраи/фолбэк из прошлого фикса) работает как задумано; причина — недоступность DNS-серверов Docker в контейнере после блокировки Google/Cloudflare DNS сетью хостера.**

## Решение

### TASK-INF-1 (DevOps, НЕМЕДЛЕННО): рабочие DNS для контейнера

Перезапустить `fences-app` с явными DNS Яндекс (проверены из контейнера: 19–27 мс):
```bash
docker rm -f fences-app
docker run -d --name fences-app --network host --restart unless-stopped \
  --dns 77.88.8.8 --dns 77.88.8.1 \
  ... (остальные параметры — как текущий запуск, образ sha-1cf4805, порт 3001, env из .env)
```
- Зафиксировать `dns: [77.88.8.8, 77.88.8.1]` в `docker-compose.yml` (прод-файл) и в шаблонах `docker run` в `SKILL_DEVOPS_PROD.md` (blue/green), чтобы фиксы не потерялись при следующем деплое.
- Не использовать 8.8.8.8/1.1.1.1 — в этой сети заблокированы.
- Верификация:
  - `docker exec fences-app node -e "require('dns').promises.resolve4('ip-api.com').then(console.log)"` — < 500 мс;
  - `curl -sf http://127.0.0.1:3001/api/health` — OK;
  - тестовый расчёт / свежая запись в БД получает город; в логе `ipLookup` появляются успешные лукапы.

### TASK-BCK-1 (Разработчик): Direct-IP фолбэк для гео-провайдеров

По образцу уже реализованного `TELEGRAM_API_IP` (телеграм пережил DNS-инцидент благодаря прямому IP):
- Файл: `src/services/admin/ipLookupService.ts`
- Добавить env-опции: `IPAPI_DIRECT_IP` (для ip-api.com, IP: 208.95.112.1) и `IPWHO_DIRECT_IP` (для ipwho.is) — при недоступности DNS-резолва запрос уходит на прямой IP с заголовком `Host`.
- Логировать факт использования Direct-IP (module `ipLookup`).
- Автотесты: DNS-провал → Direct-IP успех; Direct-IP отключён/не задан → прежнее поведение; сигнатура `getCityByIP` не меняется.
- Quality Gate: `npm test && npm run lint && npx tsc --noEmit`.
- На прод включается через `.env` при следующем деплое.

### TASK-BCK-2 (DevOps, после TASK-INF-1): бэкфилл города за период сбоя

Запустить на проде существующий идемпотентный скрипт (из прошлого фикса):
```bash
docker exec fences-app node ... prisma/scripts/backfill-estimate-city.ts
```
- Период: записи с `createdAt >= 2026-11-04`, `city IS NULL`, `ipAddress` непустой — все 3 модели (Fence/MultiFence/Gate).
- После завершения: сверить `with_city` по дням в БД, доложить сколько восстановлено.

## Критерии приёмки

1. Из контейнера `resolve4('ip-api.com')` < 500 мс, 5 замеров подряд без ETIMEOUT.
2. Новые расчёты/события получают город (свежая запись в БД с заполненным `city`, в телеграм-уведомлении есть «📍 Локация»).
3. `docker-compose.yml` (прод) и шаблоны `SKILL_DEVOPS_PROD.md` содержат `dns: 77.88.8.8, 77.88.8.1`.
4. Бэкфилл восстановил город у записей с 04.11 (где IP резолвится) — отчёт по числу обновлений.
5. TASK-BCK-1: Direct-IP фолбэк реализован, автотесты зелёные, Quality Gate зелёный; деплой по полному конвейеру (Разработчик → Тестировщик → DevOPS).
6. Логи `ipLookup` содержат успешные операции (не только ошибки).
