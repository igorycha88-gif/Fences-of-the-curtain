# ЧТЗ: Надёжный CI/CD для Production с Автоматическим Откатом

**Версия:** 1.0  
**Дата:** 2026-04-11  
**Приоритет:** CRITICAL  

---

## 1. Проблематика

### Текущие причины падений сборок:
1. **Blue-Green не работает** — GREEN запускается, проверяется, убивается, затем прямой деплой с даунтаймом
2. **Нет версионирования образов** — откат = `git reset + rebuild` (3-5 мин простой)
3. **Миграции в entrypoint** — если миграция падает, контейнер умирает, а старый уже убит
4. **Redis NOAUTH** (инцидент 2026-04-09) — env-переменные не пробросились при частичной пересборке
5. **Monitoring привязан к деплою** — при обновлении app перезапускается весь мониторинг
6. **Smoke-тесты не в пайплайне** — `smoke-test.sh` существует, но не вызывается
7. **Нет Telegram-уведомлений** при деплое

---

## 2. Решение

### Архитектура нового CI/CD:

```
Push to master2
     │
     ▼
┌─────────────────────────────────────┐
│ CI (ci.yml)                         │
│  ├── Lint + TypeCheck + Security    │
│  ├── Tests (Jest + PostgreSQL)      │
│  └── Docker Build → GHCR push       │
└──────────────┬──────────────────────┘
               │ (только если CI OK)
               ▼
┌─────────────────────────────────────┐
│ Deploy (deploy-production.yml)      │
│  1. DB Backup                       │
│  2. Pull image from GHCR            │
│  3. Start GREEN (порт 3003)         │
│  4. Health check GREEN              │
│  5. Switch nginx upstream → GREEN   │
│  6. nginx -s reload                 │
│  7. Stop OLD (BLUE)                 │
│  8. Smoke tests                     │
│  9. Telegram notification           │
│ 10. [FAIL] → auto rollback          │
└─────────────────────────────────────┘
```

---

## 3. Критерии приёмки

### AC-1: Docker-образы версионированы в GHCR
- Каждый коммит в master2 создаёт образ с тегами: `sha-XXXXX`, `latest`
- Образы хранятся в GitHub Container Registry (ghcr.io)
- Последние 10 образов сохраняются для отката

### AC-2: Blue-Green деплой с нулевым даунтаймом
- Новый контейнер (GREEN) запускается на порту 3003 параллельно с текущим (BLUE, порт 3001)
- GREEN проходит health check перед переключением
- Переключение через `nginx upstream` + `nginx -s reload` (мгновенное)
- Если GREEN не прошёл health check → он удаляется, BLUE продолжает работать

### AC-3: Автоматический откат при Smoke-тестах
- После переключения запускаются smoke-тесты
- Если хотя бы 1 критический тест падает → автоматический откат:
  - nginx upstream переключается обратно на BLUE
  - GREEN контейнер удаляется
  - Отправляется Telegram-уведомление об откате

### AC-4: Мгновенный ручной откат
- `rollback-production.yml` позволяет выбрать конкретный образ из GHCR
- Откат не требует пересборки — образ уже готов
- Время отката: < 30 секунд

### AC-5: Мониторинг отделён от деплоя приложения
- `docker-compose.monitoring.yml` НЕ перезапускается при деплое app
- Мониторинг обновляется только через отдельный workflow или вручную

### AC-6: Telegram-уведомления
- Успешный деплой: commit, время, версия
- Откат: причина, commit, время
- Ошибка деплоя: детали

### AC-7: Pre-deploy проверки
- Проверка .env файла
- Проверка свободного места на диске (> 1GB)
- Проверка что PostgreSQL и Redis доступны
- Проверка что текущее приложение здорово (или прямое развёртывание если нет)

### AC-8: Миграции БД безопасны
- Миграции выполняются в entrypoint контейнера
- GREEN контейнер применяет миграции до health check
- Если миграция падает → GREEN умирает → health check не проходит → BLUE продолжает

## 5. Риски и митигация

| Риск | Митигация |
|------|-----------|
| GHCR недоступен | Fallback на локальную сборку на VPS |
| Миграция ломает БД | Pre-deploy backup + миграция в GREEN контейнере (не влияет на BLUE) |
| Nginx reload падает | Проверка `nginx -t` перед reload |
| Диск переполнен | Pre-deploy проверка свободного места |
| Два контейнера одновременно (память) | GREEN стартует, health-check, переключение, BLUE стоп — >30с overlap на 4GB RAM допустимо |
