## 4. Функциональные требования

### ФТ-1. Трекинг кликов по телефону на ВСЕХ публичных tel:-ссылках
Во всех перечисленных местах добавить `onClick={() => { metrikaEvents.phoneClick(); trackEvent(EVENT_NAMES.PHONE_CLICK); }}`
(где уже есть `metrikaEvents.phoneClick()` — добавить только `trackEvent`):
- `zabory-navesy/[slug]/page.tsx`, `navesy-pod-klyuch/page.tsx`, `AboutCTA.tsx`, `PhoneLinkButton.tsx`
- Административные `tel:` (ClientInfo) НЕ трогаем.

### ФТ-2. Агрегация гео посетителей (Redis)
В `POST /api/analytics/events`:
- При `sessionJustStarted === true` (уникальный посетитель) → `getCityByIP(ip)`:
  - город найден → `hincrby analytics:geo:daily:<МСК-дата> <city> 1`
  - не найден/ошибка → `hincrby analytics:geo:daily:<МСК-дата> 'Не определён' 1` (не ронять запрос при ошибке lookup)
- `expire` 30 дней (как у daily)
- Lookup выполнять асинхронно, без блокировки ответа; ошибки логировать через `logger.error` с контекстом

### ФТ-3. Сервис: новые блоки в `businessMetricsService`
Расширить `BusinessMetrics` (все данные — Redis, заказные фильтры serviceType/managerId к этим блокам НЕ применяются, только период):
- `phoneClicks: { total: number; previousTotal: number; trend: number | null; trendDirection: 'up'|'down'|'neutral'; byDay: { date: string; count: number }[] }`
  — сумма `phone_click` по `analytics:daily:<date>` за период; previous — за предыдущий период (тот же принцип, что у KPI)
- `visitorGeo: { city: string; count: number; percentage: number }[]`
  — агрегация `analytics:geo:daily:<date>` за период, топ-10 по count, % от суммы; пусто → `[]`
- Логирование: начало/конец чтения Redis-блоков, ошибки с контекстом; Redis недоступен → блоки с нулями/пустым массивом + `logger.error`, основной ответ НЕ ломать

### ФТ-4. API: проброс новых блоков
`GET /api/admin/business-metrics` — ответ дополняется `phoneClicks` и `visitorGeo` (без изменений контракта остальных полей).

### ФТ-5. Страница дашборда
- Новая KPI-карточка «Клики по телефону» (значение за период + тренд) — в kpi-grid
- Блок «Клики по телефону по дням» — `BarList` (label = дата, count, display = шт)
- Блок «Гео посетителей» — `BarList` топ-10 городов (count, %)
- Состояние «нет данных» для обоих блоков (пустые массивы → «Нет данных», не падать)

### ФТ-6. Экспорт XLSX
`GET /api/admin/business-metrics/export` — добавить листы:
- «Клики по телефону»: дата / количество + строка «Итого»
- «Гео посетителей»: город / количество / %

### ФТ-7. Метрики в `/metrics/tracking` (Prometheus, заголовок X-Monitoring-Key)
Живая проверка 2026-08-29: `business_events_24h{event_type="phone_click"}` уже отдаётся автоматически — доработка НЕ нужна.
Добавить в `src/lib/tracking-metrics.ts`:
- Чтение `analytics:geo:daily:<МСК-дата>` (сегодня + вчера — окно 24ч)
- Новая метрика: `business_geo_visitors_24h{city="<город>"} <count>` (gauge, топ-10 + other)
- Отдаётся на `/api/metrics/tracking` → nginx `/metrics/tracking`

## 7. Критерии приёмки

1. Клик по любой публичной `tel:`-ссылке отправляет `phone_click` во внутренний трекинг (+ Метрика сохраняется)
2. Первый визит сессии инкрементит `analytics:geo:daily:<дата>` (город или «Не определён»)
3. API возвращает `phoneClicks` (total + тренд + byDay) и `visitorGeo` (топ-10) для выбранного периода
4. Дашборд показывает KPI «Клики по телефону» и оба новых блока; пустые данные → «Нет данных», без ошибок
5. Экспорт содержит 2 новых листа
6. Redis недоступен → дашборд работает (блоки пустые), в логах ошибка
7. `npm test && npm run lint && npx tsc --noEmit` — зелёные
8. Логирование во всех изменённых backend-файлах; автотесты на новый функционал (happy + error + edge)

## 8. Риски

| Риск | Митигация |
|------|-----------|
| Исторических данных нет (гео и клики копятся с момента релиза) | Ожидаемо: блоки покажут «Нет данных» до накопления; сообщить пользователю |
| ip-api.com rate-limit (45 req/min) | Кэш `geo:<ip>` уже есть; lookup только на старте сессии |
| Дней в периоде «year» = 365 ключей Redis | pipeline-чтение, ключи лёгкие (hash ≤ N полей); приемлемо |
| sendBeacon на iOS может теряться | Существующее поведение, не блокирует |
